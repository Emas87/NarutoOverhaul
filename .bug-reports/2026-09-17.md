# Audit report - NarutoOverhaul - 2026-09-17
2 bugs (1 high, 1 medium, 0 low), 1 improvements

## Bugs

### High - The mod's 4 custom network packet handlers trust a client-supplied player index instead of the real sender, letting any client forge another player's Chakra/Stamina/Transformation/MoonLordBlessing state
- Location: Common/Players/TransformationPlayer.cs:392-411 (`HandlePacket`, reads `byte playerIndex` from the packet body at :394 and writes to `Main.player[playerIndex]` at :398 instead of using the `whoAmI` parameter it already has); Common/Players/MoonLordBlessingPlayer.cs:56-71 (`HandlePacket`, identical shape: :58/:61); Common/Players/ChakraPlayer.cs:177-181 (`HandleCorrectionPacket`, via Common/Systems/ResourceCorrectionPacket.cs:29-32 `Receive`); Common/Players/StaminaPlayer.cs:189-193 (`HandleCorrectionPacket`, same `Receive` helper); dispatched from NarutoOverhaul.cs:10-29 (`Mod.HandlePacket`, which hands every inbound packet - regardless of whether this instance is running as server or client - straight to one of the four handlers above with no sender/role check of its own)
- Description: tModLoader's `Mod.HandlePacket(BinaryReader reader, int whoAmI)` already tells the receiver who actually sent the packet (`whoAmI` - the sending client's player slot when received on a server). None of the four handlers use it for that purpose. Instead:
  - `TransformationPlayer.HandlePacket` and `MoonLordBlessingPlayer.HandlePacket` both read a second, attacker-controlled `playerIndex` byte out of the packet's own payload and apply the update to `Main.player[playerIndex]` - a completely different player than whoever actually sent the packet. On a server, this write also gets relayed to every other client (`relay.Send(-1, whoAmI)`), so one malicious client can rewrite and broadcast state belonging to any other connected player.
  - `ChakraPlayer.HandleCorrectionPacket`/`StaminaPlayer.HandleCorrectionPacket` have an even simpler problem: the only code that is supposed to *send* `SyncChakraCorrection`/`SyncStaminaCorrection` is `ResourceCorrectionPacket.Send`, which early-returns unless `Main.netMode == NetmodeID.Server` (i.e. "only the server ever sends this, to one specific client"). But that guard only constrains the mod's own legitimate call sites - it does nothing to stop a modified client from constructing that exact packet type itself and sending it straight to the server. Neither `HandleCorrectionPacket` method checks `Main.netMode` or the sender's identity before blindly executing `Main.player[playerIndex].GetModPlayer<ChakraPlayer>().Chakra = chakra;` (or the Stamina equivalent) with attacker-chosen `playerIndex` *and* attacker-chosen `chakra`/`stamina` values - on the server's own authoritative copy.
  This is the same "trust the client" gap the project already paid down once for `RasenganItem`/`GentleFistItem`'s local UseAnimation/Shoot desync (commit f571db9) and is flagging again for `TaijutsuKickItemBase` (2026-09-16 report) - but this instance is a genuine network trust boundary, not just a same-client sequencing gap, and the resource-correction half lets an attacker write an arbitrary numeric value, not just replay a stale one.
- Failure scenario: A player running a trivially modified tModLoader client (no server-side anti-cheat exists to catch this - the mod itself is the only thing that validates these packets) can, in any multiplayer session:
  1. Send a `SyncChakraCorrection` (or `SyncStaminaCorrection`) packet straight to the server with their own `playerIndex` and `chakra = 99999`, instantly refilling their Chakra/Stamina to any value on the server's authoritative state - free, repeatable, unlimited jutsu/Taijutsu spam with zero resource cost, bypassing every `TrySpendChakra`/`TrySpendStamina` gate in the mod.
  2. Send the same packet type with a *different* player's `playerIndex` to zero out (or inflate) another connected player's Chakra/Stamina against their will.
  3. Send a `SyncTransformation` packet naming another player's index to force that player's `ActiveFormIndex` to `KamuiPhaseFormIndex` (which makes `TransformationPlayer.CanBeHitByNPC`/`CanBeHitByProjectile` return false on every client that received the forged relay - i.e. broadcasts apparent NPC/projectile immunity for a player who never activated or paid for the form) or reset it to `-1` to strip someone's active form mid-fight.
  4. Send a `SyncMoonLordBlessing` packet naming another player's index to forge their `HasKaguyaBlessing` flag, which `MoonLordAssistGlobalNPC.FindBlessedPlayer` (Common/GlobalNPCs/MoonLordAssistGlobalNPC.cs:61-74) reads server-side to decide who gets the periodic 100-damage homing assist against Moon Lord - letting an attacker either grant themselves that assist without ever consuming `OtsutsukiChakraFragmentItem`, or strip a legitimate holder's flag.
- Suggested fix: In all four handlers, stop trusting any player-index byte embedded in the packet payload for the *write target*. Use `whoAmI` (the actual sender, already passed in by tModLoader) as the player being updated - `Main.player[whoAmI].GetModPlayer<...>()` - and drop the redundant `playerIndex`/`Write((byte)Player.whoAmI)` field from `SyncPlayer` entirely (or keep it only for logging/assertions, never for indexing). For the two correction-packet handlers specifically, also add `if (Main.netMode == NetmodeID.MultiplayerClient) { /* apply locally, this is the expected direction */ }` vs. reject/ignore on the server (a client should never legitimately be the origin of a `*Correction` packet) so a forged correction sent to the server is dropped instead of applied.

### Medium - extract_tmod.py's rawimg decoder crashes with an unhelpful raw exception (instead of a clear error) on a truncated or corrupt `.rawimg` entry
- Location: tools/extract_tmod.py:92-97 (`rawimg_to_pil`: `struct.unpack` of `version, width, height` with no sanity check, `bytearray(raw[12:12+width*height*4])` which silently truncates instead of raising if `raw` is shorter than the header claims, then `Image.frombytes(...)` at :97)
- Description: `rawimg_to_pil` takes `width`/`height` straight from the file's own header with no validation (not checked for being positive, nor for being consistent with the actual amount of pixel data present). If the payload is shorter than `width * height * 4` bytes - a truncated download, a `.tmod` whose file-table `length`/`compressedLength` don't actually match its real content (see the adjacent, unvalidated `extract_file` at :83-89, which slices `data[off:off+clength]` with the same no-bounds-check pattern one level up), or simply a `.rawimg` in a version/format this script doesn't fully understand - the `raw[12:12+width*height*4]` slice silently returns fewer bytes than expected (Python slicing never raises on an out-of-range end index) instead of erroring where the real problem is. The BGRA swap loop at :95-96 then either produces a body whose length isn't a multiple of 4 (risking an `IndexError` on `body[i+2]`) or, more commonly, `Image.frombytes("RGBA", (width, height), bytes(body))` raises a bare `ValueError` ("not enough image data") with no context about which entry or file caused it.
- Failure scenario: Running `tools/extract_tmod.py extract SomeWorkshopMod.tmod Some/Path.rawimg out.png` against a Workshop mod whose `.tmod` is partially corrupted, was updated mid-download, or simply isn't laid out exactly the way this script assumes crashes with a generic Python traceback pointing at `Image.frombytes` (or an `IndexError` inside the byte-swap loop) instead of a clear "this .rawimg entry is truncated / malformed" message - the kind of confusing failure this script's own extensive header-comment culture (see the file's docstring and the CLAUDE.md write-ups this project keeps for its asset tooling) is otherwise careful to avoid.
- Suggested fix: After unpacking `width`/`height`, validate they're positive and that `len(raw) >= 12 + width * height * 4` before building `body`; raise a clear `ValueError` naming the shortfall (expected vs. actual byte count) if not. Optionally also validate in `extract_file` that `off + clength <= len(data)` for the same reason, so a malformed file-table entry fails loudly at the point it's read rather than producing a silently-truncated `raw` that only surfaces as a confusing error two functions later.

## Improvements

### robustness - extract_tmod.py's `extract` command raises a bare IndexError instead of the usage message when called with too few arguments
- Location: tools/extract_tmod.py:100-113 (`main`: the `len(sys.argv) < 3` guard at :101 only covers `cmd`/`tmod_path`; the `extract` branch at :112-113 unconditionally does `sys.argv[3], sys.argv[4]` with no length check, unlike the `list` branch at :108 which correctly guards its own optional `sys.argv[3]`)
- Current: `tools/extract_tmod.py extract SomeMod.tmod` (forgetting the in-archive path and/or output path) raises `IndexError: list index out of range` instead of the module's own `__doc__` usage string that every other malformed-invocation path in this file already shows.
- Proposed: Check `len(sys.argv) < 5` for the `extract` branch (mirroring the existing `len(sys.argv) < 3` guard at the top of `main`) and `sys.exit(__doc__)` on failure, the same pattern already used everywhere else in this file.
- Risk: trivial - purely additive argument-count check, no change to any success-path behavior.
