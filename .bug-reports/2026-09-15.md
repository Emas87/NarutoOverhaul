# Audit report - NarutoOverhaul - 2026-09-15
1 bugs (0 high, 1 medium, 0 low), 2 improvements

## Bugs

### Medium - slice_fx_sheet.py silently drops content from the last VFX frame when the sheet height isn't an exact multiple of `--rows`
- Location: tools/slice_fx_sheet.py:85 (`src_row_h = sheet.height // rows`), :94-99 (`slice_sheet`'s per-row crop loop)
- Description: `src_row_h` is computed with integer floor division. Every row's crop window is derived from `src_row_h` (`y0 = i * src_row_h + row_margin`, `y1 = (i + 1) * src_row_h - row_margin`), so the last row's `y1` is `rows * src_row_h - row_margin`, not `sheet.height - row_margin`. Whenever `sheet.height % rows != 0` (the common case for an AI-generated raw sheet, which has no reason to land on a multiple of the frame count - see the file's own header noting this generalizes `generate_armor_sheet.py`'s per-cell logic, which had the exact same class of silent-clip bug fixed on 2026-09-14 for `HEAD_TOP_MARGIN`), the bottom `sheet.height % rows` pixels of the raw sheet - which live inside the last frame's row - are never included in any row's crop and are silently lost. `Image.crop()` and the later `_key_and_trim`/`_center_on_canvas` calls raise no error and print nothing.
- Failure scenario: Running `tools/slice_fx_sheet.py --sheet raw_sheet.jpeg --rows 6 --frame-w 150 --frame-h 150 --out Content/Projectiles/Bursts/SomeBlastProjectile.png` on a nano-banana-generated sheet whose height isn't divisible by 6 (e.g. a 1024px-tall generation, 1024 % 6 = 4) truncates the bottom few pixels of content out of the last animation frame's source row before it's even cropped/trimmed, producing a landed VFX frame that's missing part of its art with no warning - the same "quietly ships a clipped frame" failure mode the 2026-09-10/09-14 Head-frame bug already burned this repo on once.
- Suggested fix: Distribute the remainder instead of dropping it - e.g. compute each row's `y0`/`y1` from `round(i * sheet.height / rows)` / `round((i + 1) * sheet.height / rows)` so every row (including the last) spans its true proportional slice of `sheet.height`, or at minimum set the last row's `y1` explicitly to `sheet.height - row_margin` instead of `rows * src_row_h - row_margin`.

## Improvements

### robustness - pixellab_generate.py's job-polling loop has no timeout or max-retry cap
- Location: tools/pixellab_generate.py:92-106 (`edit_image`'s `while True: time.sleep(5); status = _get(...)` poll loop)
- Current: After submitting a background job, the loop polls every 5 seconds forever until the API reports `"completed"` or `"failed"`; any other status (including one that never changes, e.g. the job silently stalls in `"queued"`/`"processing"` on PixelLab's side) keeps the script polling indefinitely with no elapsed-time check, no attempt counter, and no way to abort except killing the process.
- Proposed: Track elapsed time (or attempt count) and raise a `RuntimeError` past a sane ceiling (e.g. 10-15 minutes), so a stuck job fails loudly instead of hanging the invoking shell/CI step forever.
- Risk: trivial - purely additive (a counter + a raise), doesn't change the success-path behavior.

### documentation - ChakraPlayer's SendCorrection comment states an assumption this codebase already proved false
- Location: Common/Players/ChakraPlayer.cs:168-171 (comment above `SendCorrection`)
- Current: The comment reads "PainBoss's Preta Path drains chakra server-side from AI(), which only ever touches the server's own authoritative copy - without this, the client never learns their chakra was spent." That claim (`NPC.AI()` "only ever touches the server's own authoritative copy") is exactly the false assumption `.bug-reports/2026-09-08.md` through `2026-09-14.md` flagged and that was fixed in `PainBoss.DoPreta` on 2026-09-14/15 (`Main.netMode != NetmodeID.MultiplayerClient` guard added around the drain) precisely because `NPC.AI()` runs on every peer's own local shadow simulation, not just the server's. The comment was never updated to reflect that the guard is now required in `DoPreta` itself, not just this correction packet.
- Proposed: Reword the comment to describe the actual invariant (`DoPreta` now guards the spend itself server-side; `SendCorrection` exists to push that authoritative value to the drained player's own client, which never gets a spend call to derive it from) so a future contributor writing a new server-triggered resource drain doesn't copy the stale "AI() is server-only" reasoning into a fresh ungated call site.
- Risk: trivial - comment-only change, no behavior affected.
