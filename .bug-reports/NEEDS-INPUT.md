## Design decisions
### Whether to rate-limit/dedupe HiraishinMarkerSystem's HandleAddMarkPacket per sender
- Report: .bug-reports/2026-09-21.md
- Location: Common/Systems/HiraishinMarkerSystem.cs:123-132
- The decision: the tile-type/in-world validation above stops fake marks, but a client could still
  spam requests for a real seal tile it just watched someone else place, forcing redundant
  `SyncToClients()` broadcasts. Low real-world impact (list capped at 10, `AddMark` already no-ops
  on duplicates).
- Options: A) ship the validation fix alone and accept the redundant-broadcast spam as harmless
  B) also add a per-sender cooldown/dedupe window before calling `AddMark`

### Whether TailedBeastBoss's ground-tile cache should re-verify the single cached tile every tick
- Report: .bug-reports/2026-09-21.md
- Location: Content/NPCs/Bosses/TailedBeastBoss.cs:244-279 (`ApplyGroundedMovement`)
- The decision: the cache (added in `cd86f60`) never re-checks the previously-found ground tile
  while the boss stays on the same horizontal tile, so mining out the ground under a stationary
  boss leaves it floating. The commit's own comment calls this "acceptable"; a prior report
  suggested a cache should be "a hint that's cheaply re-validated, not trusted unconditionally."
- Options: A) keep the current O(1)-when-unchanged behavior and accept the narrow floating-boss
  edge case as a documented tradeoff B) add a per-tick `WorldGen.SolidTile(centerTileX,
  _cachedGroundTileY)` re-check (still far cheaper than the full up-to-120-tile scan it replaced)
  and fall back to a full scan only when that single check fails
