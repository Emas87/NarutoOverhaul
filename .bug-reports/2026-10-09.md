## Bugs
### Medium - `generate_boss_sprites.py`'s boss data is stale: wrong canvas/frame layout for all 6 bosses it lists, and the 7th boss is missing entirely
- Location: `tools/generate_boss_sprites.py:13-14` (usage comment), `:25` (`FRAMES_PER_BLOCK = 6`),
  `:51-112` (`BOSSES` dict, 6 entries: Haku/Kaguya/Kakuzu/Madara/Orochimaru/Pain)
- Description: the script's own usage comment says `tools/generate_boss_sprites.py` with no args
  "regenerate[s] all 7 boss sheets in place," but `BOSSES` only has 6 keys - `TailedBeastBoss`
  (Shukaku) is absent, so a full regen run would silently skip it. For the 6 it does list, every
  `canvas_h` and every block's frame count is wrong relative to both the real committed art and
  `ANIMATION_PIPELINE.md`'s documented, ground-truthed layout (which matches each boss's own
  `IdleFrameCount`/`MeleeFrameCount`/`CastFrameCount`/... constants and `Main.npcFrameCount[NPC.type]`
  assignment in its `.cs` file). Verified directly against the actual files via `identify`:
  | Boss | script `canvas_w x canvas_h`, blocks×`FRAMES_PER_BLOCK` | real PNG / `.cs` frame counts |
  |---|---|---|
  | Haku | 40x56, 3 blocks × 6 = 18 frames | `HakuBoss.png` 64x1400 = 25 frames (10+7+8, per `HakuBoss.cs`) |
  | Kaguya | 46x68, 3×6=18 | `KaguyaBoss.png` 73x840 = 15 frames (4+7+4) |
  | Kakuzu | 46x58, 2×6=12 | `KakuzuBoss.png` 62x616 = 11 frames (4+7) |
  | Madara | 48x64, 3×6=18 | `MadaraBoss.png` 52x728 = 13 frames (5+4+4) |
  | Orochimaru | 44x60, 3×6=18 | `OrochimaruBoss.png` 78x896 = 16 frames (4+6+6) |
  | Pain | 44x62, 2×6=12 | `PainBoss.png` 85x560 = 10 frames (4+6) |
  Every real sheet's frame height is 56px (matching `ANIMATION_PIPELINE.md`'s table), but the
  script's `canvas_h` values (56/68/58/64/60/62) and fixed `FRAMES_PER_BLOCK = 6` never match any of
  them, and `canvas_w` is wrong for all 6 too.
- Failure scenario: anyone following the script's own documented usage (or CLAUDE.md's general
  "re-run the generator after an asset/animation change" pattern used for the sibling
  `generate_town_npc_sprites.py`) to regenerate a boss sheet - e.g. after a palette tweak - would
  overwrite the real, currently-correct `<Boss>.png` with a new file whose block/frame structure no
  longer matches that boss's `FindFrame` state machine (which still indexes by the real
  `IdleFrameCount`/`MeleeFrameCount`/`CastFrameCount` constants, unaware the underlying sheet now has
  fewer/misaligned frames per block), corrupting that boss's in-game animation, and `TailedBeastBoss`
  would be left both un-regenerated and silently unmentioned in the run's output.
- Suggested fix: update each `BossChar` entry's `canvas_w`/`canvas_h` and block list/frame-count to
  match `ANIMATION_PIPELINE.md`'s table (and that boss's real `.cs` constants) exactly - which likely
  means reworking `render_frame`'s per-block cycles to support per-block frame counts instead of one
  global `FRAMES_PER_BLOCK`, matching how `generate_town_npc_sprites.py` already varies its own block
  lengths - and add the missing `TailedBeastBoss` entry (idle/hover(8) / chase(8) / charge(7)).
  > Needs a decision: whether this procedural generator is still the intended path for future boss
  > art (in which case it's worth the rework above) or whether boss art has moved fully to the
  > nano-banana/manual pipeline described elsewhere in `ANIMATION_PIPELINE.md` for Town NPCs, in
  > which case this script should instead be deleted or clearly marked superseded so nobody runs it
  > expecting a safe regen.

- Location: `ANIMATION_PIPELINE.md:39-45` ("Town NPCs - Done" section and table)
- Current: the table lists `KakashiNPC`/`ItachiNPC`/etc. as 37x40/35x40-canvas sheets with only

  describe the procedural `generate_town_npc_sprites.py` output that's actually shipped, so the doc
  stays a reliable reference for anyone touching these sheets next (this is exactly the kind of
  stale-doc drift that let the `generate_boss_sprites.py` bug above go unnoticed).
- Risk: trivial
