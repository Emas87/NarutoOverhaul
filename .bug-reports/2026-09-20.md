## Bugs

### High - TailedBeastBoss silently self-deactivates the instant its current target dies, even while other players are still fighting it, instead of following every sibling boss's despawn pattern
- Location: Content/NPCs/Bosses/TailedBeastBoss.cs:198-211 (`AI()`'s target-invalid branch: `NPC.active = false; NPC.netUpdate = true; return;`)
- Description: Every other boss in this codebase (`HakuBoss.cs:142-147`, `KakuzuBoss.cs:174-179`, `MadaraBoss.cs:195-200`, `OrochimaruBoss.cs:231-236`) handles the identical "current target is dead/inactive" case with the same pattern: `NPC.velocity.Y -= 0.2f; NPC.EncourageDespawn(10); return;` - a soft nudge that lets the natural vanilla despawn timer run down over several ticks, during which `TargetClosest()` on the next tick can still re-acquire a different, still-alive nearby player. `TailedBeastBoss` instead hard-sets `NPC.active = false` directly. `AI()` runs as a local shadow simulation on every connected peer (server and each client independently, from the same synced state) - this is the exact invariant this codebase's own `HiraishinMarkerSystem.cs` comment and the 2026-09-15 report on `PainBoss` both call out as the recurring source of bugs here. Since `NPC.target` is derived identically on every peer from the same synced player-death state, all peers - including the server - hit this branch in the same tick and each directly flips their own copy of `.active` off without going through `NPC.checkDead()`/any kill-credit path. On the server this means the boss NPC slot goes inactive immediately, with no chance for `TargetClosest()` to ever run again for it, and without triggering `OnKill()` (no loot, no `StoryProgressSystem.DownedShukaku` flag set) - contrary to the very next line's own comment claiming this is done specifically to avoid granting "kill credit/loot the way NPC.checkDead() would" as if that were the risk being avoided, when the real risk is the opposite: an active boss fight with HP remaining just vanishing with nothing to show for it.
- Failure scenario: In a 2+ player fight against Shukaku (TailedBeastBoss), if the single player currently set as `NPC.target` dies (a very ordinary event against a boss dealing 40 contact damage), the very next `AI()` tick deactivates the boss for everyone, mid-fight, regardless of how much of its 12000 HP remains and regardless of how many other players are still actively engaging it right next to it - there is no grace window to retarget a still-alive nearby player the way `EncourageDespawn`'s multi-tick countdown allows. In solo play (the common case), a player dying to their own boss fight causes the boss to disappear entirely rather than remaining for a subsequent attempt, and it disappears via a silent slot deactivation rather than the same graceful despawn path every sibling boss already relies on.
- Suggested fix: Replace the `NPC.active = false; NPC.netUpdate = true;` branch with the same `NPC.velocity.Y -= 0.2f; NPC.EncourageDespawn(10); return;` pattern used by every sibling boss, so a still-alive nearby player can be re-acquired as target before the boss actually times out, and so an eventual despawn goes through the same vanilla path (not `NPC.active` toggled directly by every peer independently).
> Needs a decision: the file's own comment argues `EncourageDespawn` "doesn't work here" because a dead player's screen keeps showing the boss (resetting the despawn timer) and because `boss=true` exempts it from off-screen despawn - but this exact scenario (a boss NPC, target dies, other players may or may not be nearby) is identical for `HakuBoss`/`KakuzuBoss`/`MadaraBoss`/`OrochimaruBoss`, all of which are also `boss=true` and all of which already ship with plain `EncourageDespawn(10)` with no reported despawn-failure issue. Worth confirming (in a real multiplayer test, not just reasoning about it) whether that premise is actually true before assuming the sibling pattern is safe to copy verbatim - if it genuinely isn't, the right fix is a small explicit no-target grace timer gated behind `Main.netMode != NetmodeID.MultiplayerClient` (so only the server/singleplayer authoritatively decides to deactivate, not every client's shadow copy independently) rather than reintroducing the current unconditional-on-every-peer deactivation.

## Improvements

### Performance - TailedBeastBoss.ApplyGroundedMovement rescans up to 120 tiles from scratch every single tick instead of tracking the ground it already found
- Location: Content/NPCs/Bosses/TailedBeastBoss.cs:248-286 (`ApplyGroundedMovement`)
- Current: Every `AI()` tick (so on the server and on every connected client's shadow copy, per the same peer-count multiplier noted above), this method starts a fresh `for` loop from the NPC's current top tile and calls `WorldGen.SolidTile` up to `GroundScanRangeTiles` (120) times to re-find the ground surface, even on ticks where the NPC is already resting motionless on a known surface and nothing about the terrain under it has changed.
- Proposed: Cache the last-found `groundTileY` and, when the NPC hasn't moved horizontally past a tile boundary, only re-verify a small window around the cached value (falling back to the full scan only when that quick check misses, e.g. after a horizontal move or the ground being dug out) - the same "verify-then-fall-back-to-full-scan" shape already used elsewhere in this codebase for similar per-tick terrain probes.
- Risk: low - purely an internal optimization to an already-correct result; would need care to still detect terrain that changes out from under a stationary boss (a player digging out the ground it's standing on), so the cache should be a hint that's cheaply re-validated, not a value trusted unconditionally.
