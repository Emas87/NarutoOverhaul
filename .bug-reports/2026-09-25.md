## Bugs

### Low - `GenjutsuGlobalNPC.FleeMovement` still keeps fleeing a caster who has since died (unfixed since 2026-09-24)
- Location: Common/GlobalNPCs/GenjutsuGlobalNPC.cs:77-82 (`FleeMovement`) vs Common/GlobalNPCs/GenjutsuGlobalNPC.cs:53-58 (`PuppetMovement`)
- Description: Confirmed still present by re-reading the file this run. `PuppetMovement`'s guard is `ControllingPlayerIndex < 0 || !Main.player[...].active || Main.player[...].dead` and falls through to `return true` (resume normal AI) if the controller has died. `FleeMovement`'s guard is only `ControllingPlayerIndex < 0 || !Main.player[...].active` - a dead player is still `active` in Terraria (the entity persists until respawn), so this passes and `FleeMovement` keeps computing `away = npc.Center - deadPlayer.Center`, driving the feared NPC away from the fixed point where that player died instead of resuming normal AI the way the puppet case does.
- Failure scenario: A player casts `GenjutsuNightmareItem` (fear) on an enemy, then dies before the ~3+ second fear duration expires. For the remainder of that window the feared NPC keeps fleeing the player's death location instead of returning to normal behavior - broken/frozen-looking AI right when a party member just died and correct enemy behavior matters most.
- Suggested fix: Add `|| Main.player[ControllingPlayerIndex].dead` to `FleeMovement`'s early-return condition, matching `PuppetMovement` exactly.

## Improvements

### Performance - `AnimalMinionProjectile.FindTarget` scans all `Main.maxNPCs` every tick per active minion, the same anti-pattern just fixed for `ShadowCloneProjectile` (new)
- Location: Content/Minions/AnimalMinionProjectile.cs:246-270 (`FindTarget`); contrast with the already-shipped fix in Content/Minions/ShadowCloneProjectile.cs:27-34,86-123 (commit `fbe8108`, 2026-09-23)
- Current: `AnimalMinionProjectile` is the shared base for all 6 animal-summon minions (Bulldog Hound, Scout Hound, Ninja Hound, Slug, Toad, Snake - see Content/Minions/*MinionProjectile.cs). Its `FindTarget`, called unconditionally from `AI()` every tick, does a full unthrottled `for (i = 0; i < Main.maxNPCs; i++)` (200-entity) scan with no caching, no early-out and no rescan interval - exactly the pattern that was identified as a real perf problem and fixed one file over in `ShadowCloneProjectile.FindTarget` two days ago (cache the closest target, re-scan only every 10 ticks, drop the cache the instant it's no longer chaseable). Since these are genuine vanilla `Projectile.minion = true` summons, they're correctly bounded by the player's `maxMinions` slot budget (unlike Shadow Clones' original unbounded-stacking bug), but a fully-decked-out summoner can still have several of these minions active simultaneously (one per animal type, each a separate minion slot), each independently re-scanning all 200 NPC slots every single tick.
- Proposed: Port the same cache-and-throttle approach already shipped for `ShadowCloneProjectile.FindTarget` into `AnimalMinionProjectile.FindTarget` (private `cachedTarget`/`scanCooldown` fields, drop the cache when `!cachedTarget.CanBeChasedBy(...)`, full rescan only every N ticks) so the fix lands once in the shared base class and benefits all 6 animal minions at once, instead of needing to be rediscovered and reapplied per-subclass later.
- Risk: trivial - this is a straight port of an already-verified, already-shipped fix from a sibling file; the externally-visible behavior (which NPC gets chased) is unchanged, only how often it's recomputed.

### Robustness/Performance - `HitDebugLoggerPlayer` is still an unremoved TEMP debug hook attached to every player (unfixed since 2026-09-24)
- Location: Common/Players/HitDebugLoggerPlayer.cs:12-38
- Current: Confirmed still present and unmodified this run. The class's own header comment still calls it a "TEMP debug aid ... Remove once boss hitbox/position issues are confirmed fixed" for the `TailedBeastBoss` investigation that the 2026-09-21/22 ground-cache fixes (`cd86f60`, `81016d7`) closed out. It's still an unconditional `ModPlayer` override with no debug-flag gate, so `PostHurt` still runs a full `Main.maxNPCs` (200) scan plus 1-3 `Mod.Logger.Info` disk writes on every single hit any player takes, anywhere, for any reason.
- Proposed: Delete the class (its own stated removal condition is already met), or gate it behind a debug-only flag if it might be needed again.
- Risk: trivial - debug-only instrumentation with zero gameplay effect either way.

### Robustness - `smoke_test_server.sh` still always exits 0 even on a detected FAIL/exception (unfixed since 2026-09-12)
- Location: tools/smoke_test_server.sh:19-35
- Current: Confirmed still present this run - the server launch line still ends in `|| true`, and neither the `FAIL: server did not report a clean start` branch nor the `WARNING: exception-like text found` branch is followed by `exit 1`, so the script's exit code is always 0 regardless of what it printed.
- Proposed: Track whether either failure condition was hit and `exit 1` at the end (or at each failure branch) so a CI/automation caller can actually gate on this script's exit code.
- Risk: trivial - purely additive, no change to detection logic.

### Robustness - `pixellab_generate.py`'s `edit_image` polling loop still has no timeout/max-retry cap (unfixed since 2026-08-08/2026-09-10)
- Location: tools/pixellab_generate.py:92-106
- Current: Confirmed still present this run - `while True: time.sleep(5); ...` only exits on `"completed"`/`"failed"` status from the remote API; a job stuck in `"pending"`/`"processing"` forever polls indefinitely with no way to abort short of killing the process.
- Proposed: Track elapsed time/poll count and raise a `RuntimeError` past a max wait (e.g. 10-15 minutes) so a hung job fails loudly instead of hanging the art pipeline invisibly.
- Risk: trivial - purely additive bound-checking, no change to the success path.
