## Bugs

### High - HiraishinMarkerSystem's new HandleAddMarkPacket trusts client-supplied tile coordinates with zero validation, letting any connected client inject or flood the shared, server-authoritative warp-point registry
- Location: Common/Systems/HiraishinMarkerSystem.cs:123-132 (`HandleAddMarkPacket`), reached from `NarutoOverhaul.cs:28-29`; the vulnerable client-facing sender is `SendAddMarkRequest` at Common/Systems/HiraishinMarkerSystem.cs:109-121
- Description: This packet/handler pair was added yesterday (`626c43a`) specifically to fix a real bug - a non-host client's locally-placed Hiraishin seal never reaching the server's authoritative `MarkedTiles` list. The fix is correct as far as it goes, but the handler does none of the validation every other custom packet handler in this codebase does for attacker-controlled input: it doesn't call `WorldGen.InWorld(x, y)` (unlike `MinatoKunaiProjectile.IsSolid`, which does exactly this check on the same kind of tile coordinate), and it never verifies a `HiraishinSealTile` (or any tile at all) actually exists at `(x, y)` before calling `AddMark`. Contrast with `TransformationPlayer.HandlePacket`/`MoonLordBlessingPlayer.HandlePacket`, both of which have an explicit comment about never trusting attacker-controlled data from the payload - this handler has no such guard at all, and unlike those two (which only ever touch the sending player's own per-player state), this one mutates a single shared, world-wide list every player relies on for Hiraishin Warp.
- Failure scenario: A modified/malicious client sends repeated `HiraishinAddMark` packets with arbitrary (including out-of-world or negative) X/Y coordinates. Each one that isn't a duplicate and isn't already at the `MaxMarks = 10` cap gets added straight into `HiraishinMarkerSystem.MarkedTiles` and broadcast to every connected player via `SyncToClients()`. This lets one client (a) fill all 10 warp slots with junk before any real seal can register, permanently starving the shared warp network for the whole server until someone manually figures out which entries are fake and mines out real seals to force a `RemoveMark`/re-add cycle (there's no way to remove a bogus entry that has no real tile backing it), and (b) cause every other player's `TransformationPlayer.HandleHiraishinWarp` to `Player.Teleport` them straight into an arbitrary location - inside solid rock, off the edge of the world, or into the void - since nothing downstream re-validates a mark before warping to it either.
- Suggested fix: In `HandleAddMarkPacket`, before calling `AddMark`, check `WorldGen.InWorld(x, y)` and that `Main.tile[x, y].HasTile && Main.tile[x, y].TileType == ModContent.TileType<HiraishinSealTile>()` (the same shape as `MinatoKunaiProjectile.IsSolid`'s bounds check, plus a tile-type check), and silently drop the packet otherwise.
> Needs a decision: whether to also rate-limit/dedupe this per sender (e.g. ignore a flood of requests from the same `whoAmI` in a short window) - the tile-type check alone stops a client from injecting completely fake marks, but a client could still spam legitimate-looking requests for a seal it just watched someone else place (a real tile, so the validation above wouldn't catch it) purely to force redundant `SyncToClients()` broadcasts. Low real-world impact (the list is capped at 10 and `AddMark` already no-ops on a duplicate `Contains` check), so may not be worth the extra complexity - but worth a call before deciding this fix is "done."

### Medium - TailedBeastBoss's new ground-tile cache (from yesterday's own perf fix) never re-verifies the single cached tile, so digging out the ground under a stationary boss leaves it floating in place instead of falling
- Location: Content/NPCs/Bosses/TailedBeastBoss.cs:244-279 (`_cachedCenterTileX`/`_cachedGroundTileY` fields and `ApplyGroundedMovement`)
- Description: Yesterday's `cd86f60` added a cache keyed only on horizontal tile (`centerTileX`) to avoid rescanning up to 120 tiles every tick. The cache is invalidated when the boss moves to a new horizontal tile, or when the last scan found no ground at all (`_cachedGroundTileY < 0`) - but never when the boss stays on the *same* horizontal tile and the previously-found ground tile stops being solid (a player mining it out from directly underneath a stationary boss). The commit's own comment acknowledges this exact gap ("a tile destroyed/placed directly under a stationary boss between horizontal moves is the one edge case this doesn't catch") and calls it "acceptable" - but this contradicts the design `2026-09-20.md`'s own Improvements section proposed for this exact change before it was written: "the cache should be a hint that's cheaply re-validated, not a value trusted unconditionally." The actual implementation trusts the cached tile unconditionally for as long as `centerTileX` doesn't change, which is precisely the case that guidance was written to avoid, and the O(1) fix (re-checking only the single cached tile with `WorldGen.SolidTile`) would have cost nothing extra in the common case.
- Failure scenario: `TailedBeastBoss` is grounded and horizontally stationary (its `AttackState.Recover` phase runs for 45 ticks doing nothing but `NPC.velocity *= 0.9f`, and the `Charge`/`Jump` telegraph windows are similarly near-stationary in X for many ticks). A player standing nearby mines out the single ground tile directly beneath the boss's `centerTileX` during one of these windows. On every subsequent tick, `ApplyGroundedMovement` keeps reusing the now-stale `_cachedGroundTileY`, holding the boss floating at its old resting height above the now-open pit indefinitely (or until the boss's horizontal chase movement happens to shift it to a different tile column, which re-triggers a full scan and lets it start falling). In a 1500-HP-per-phase boss fight against a mid/late-game player with mining tools, this is an easily reproducible, visible bug (a supposedly grounded creature hovering over open air), not just a rare edge case.
- Suggested fix: Before trusting the cache, cheaply re-verify only the single previously-found tile (`WorldGen.SolidTile(centerTileX, _cachedGroundTileY)`); fall back to the full scan only when that single check fails. This keeps the O(1) fast path for the overwhelmingly common case (nothing changed underfoot) while still catching the one case the current code silently gets wrong, exactly as the prior report's suggestion described.
> Needs a decision: this is a very narrow, low-frequency edge case (requires precise timing of digging directly under a stationary boss) - worth confirming it's worth the extra `WorldGen.SolidTile` call per tick (still far cheaper than the up-to-120-tile scan it replaced) rather than leaving it as a documented, accepted tradeoff.

## Improvements

### Robustness - AnimalMinionProjectile.FindTarget re-scans all Main.maxNPCs (200) NPCs from scratch every tick, per minion, with no early-out
- Location: Content/Minions/AnimalMinionProjectile.cs:246-270 (`FindTarget`, called once per tick from `AI()` at line 142 for every active animal/hound minion)
- Current: Every minion instance (one per player that has one summoned, since the buff-replacement pattern caps it to one per animal type per player, but a player can have several different animal minions out - e.g. a hound plus a toad plus a slug simultaneously) iterates the full `Main.npc` array (200 slots) every single tick, calling `NPC.CanBeChasedBy` and `Vector2.Distance` for every active NPC regardless of how far away it is, just to find the single nearest target within `AttackRange`.
- Proposed: Cheap early-out before the expensive `CanBeChasedBy`/`Distance` calls - a bounding-box or squared-distance check against `AttackRange` first (most of the 200 slots are either inactive or far outside range on a typical map), or only re-scan every few ticks instead of every tick, since a minion's target rarely needs to change mid-frame.
- Risk: low - this is a read-only scan with no state mutation; the only risk is a slightly stale target for a tick or two if a scan-interval throttle is added, which is imperceptible for melee-range minion AI.
