## Improvements

### Performance - ShadowCloneProjectile duplicates AnimalMinionProjectile's unbounded per-tick full-NPC-array scan, and unlike that one it isn't capped to one instance
- Location: Content/Minions/ShadowCloneProjectile.cs:77-101 (`FindTarget`); compare Content/Minions/AnimalMinionProjectile.cs:246-269 (already flagged 2026-09-21, still open, not re-detailed here)
- Current: `FindTarget` loops all `Main.maxNPCs` (200) NPCs every tick, calling `npc.CanBeChasedBy` and `Vector2.Distance` for each, with no early-out. This is the same pattern already reported for `AnimalMinionProjectile.FindTarget`, but it's a separate, independently-written copy in a different class (`ShadowCloneProjectile` doesn't inherit from `AnimalMinionProjectile`), and it's strictly worse: `ShadowCloneItem.CloneCount = 2` clones per cast (Content/Items/Weapons/Jutsu/ShadowCloneItem.cs:18), each with a 900-tick (15s) lifetime and *no upper bound on how many can be alive at once* - `UseItem` has no cooldown beyond the 35 Chakra cost and no check for existing clones before spawning more, unlike the single-instance-via-owner-buff pattern the other minions use. A player with enough Chakra regen (or a Chakra Scroll stockpile) re-casting every ~0.5s (`useTime = 30`) during a fight with many NPCs on screen (e.g. an event, or the endgame bosses' own summoned adds) stacks these scans linearly - N clones alive means N full 200-NPC scans every single tick, not amortized in any way.
- Proposed: Same fix shape as the AnimalMinionProjectile finding (early-out on first NPC within some minimum "good enough" distance, or throttle to re-scan only every few ticks and coast on the last target in between) plus, specific to this file, consider capping concurrent live clones per owner (e.g. tag spawned clones with the owner and check a running count in `UseItem` before spawning more) so a single player can't multiply the per-tick scan cost by re-casting freely.
- Risk: moderate - the scan-throttling half is a straight perf fix with no behavior change if done carefully (same class of change already scoped for AnimalMinionProjectile); a clone-count cap changes observable gameplay (how many clones can be active at once) and is a balance call, not just cleanup.
> Needs a decision: whether to cap concurrent ShadowClone instances per owner (and if so, what the cap should be), independent of the scan-throttling fix.

### Robustness - smoke_test_server.sh still always exits 0 even on a detected FAIL/exception, unfixed since first reported 2026-09-12
- Location: tools/smoke_test_server.sh:19-35
- Current: The script's own dedicated-server launch line ends in `|| true` (line 19), swallowing any nonzero exit from the `timeout`-wrapped tModLoader process, and neither the `FAIL: server did not report a clean start` branch (line 33) nor the `WARNING: exception-like text found` branch (line 35) is followed by an `exit 1` - the script always returns 0 regardless of what it printed. Confirmed still present by re-reading the file in full this run; it was not re-flagged in the 2026-09-13 through 2026-09-22 reports, but nothing in the intervening commits touches this file.
- Proposed: after the two `grep` checks, track whether either failure condition was hit and `exit 1` at the end of the script when it was (or `exit 1` immediately at each failure branch instead of falling through to the next check). Anyone/anything treating this script's exit code as a pass/fail gate (its own header comment calls it a smoke test meant to "check that ... all complete with no exceptions") is currently unable to rely on it for that.
- Risk: trivial - the fix is adding an exit code, no change to what the script detects or how it's invoked.

### Robustness - pixellab_generate.py's `edit_image` polling loop still has no timeout/max-retry cap, unfixed since first reported 2026-08-08/2026-09-10
- Location: tools/pixellab_generate.py:92-106
- Current: `while True: time.sleep(5); status = _get(...)` only exits on the job reaching `"completed"` or `"failed"` status from the remote API; a job that gets stuck in `"pending"`/`"processing"` forever (API hang, job silently dropped server-side) polls indefinitely with no way to abort short of killing the process. Confirmed still present by re-reading the full function this run; not re-flagged since 2026-09-15 but no change has landed for this file since then.
- Proposed: track elapsed time (or poll count) and raise a clear `RuntimeError` (or similar) once a max wait (e.g. 10-15 minutes) is exceeded, so a hung job fails loudly instead of hanging the whole art-generation pipeline invisibly.
- Risk: trivial - purely additive bound-checking around an existing loop, no change to the success path.
