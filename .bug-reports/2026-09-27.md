## Bugs

### Medium - `SnakeMinionProjectile`'s retreat phase self-flips direction every tick instead of retreating steadily (unfixed since 2026-09-26)
- Location: Content/Minions/SnakeMinionProjectile.cs:44-50 (`UpdateVisuals`)
- Description: Re-read the file this run - unchanged. While `retreating` is true, every tick reads and writes `Projectile.spriteDirection` in the same statement pair: `velocity.X = -spriteDirection * speed`, then `spriteDirection = velocity.X < 0 ? -1 : 1`. Since `velocity.X`'s sign is always the opposite of the `spriteDirection` value just used to compute it, the second line always flips `spriteDirection` to the opposite of what it was going into this tick, which then flips `velocity.X`'s sign again next tick, and so on for the whole ~30-tick retreat window.
- Failure scenario: Any time a player has an active Snake summon (Orochimaru/Sasuke's snake contract, `SnakeSummonScrollItem`) fighting a nearby enemy, the described lunge-then-retreat pattern never happens - the minion vibrates in place near the target instead of retreating, defeating this minion's one distinguishing behavior versus the other 5 animal minions (which just chase straight).
- Suggested fix: Recompute `spriteDirection` once, at the tick the retreat phase begins (inside `if (lungeTimer >= 30)`, right after `retreating = !retreating` flips true), store it in a dedicated `retreatDirection` field, and hold it fixed for the rest of the retreat window instead of re-deriving it from `velocity.X` every tick.

### Low - `GenjutsuGlobalNPC.FleeMovement` still keeps fleeing a caster who has since died (unfixed since 2026-09-24)
- Location: Common/GlobalNPCs/GenjutsuGlobalNPC.cs:77-82 (`FleeMovement`) vs Common/GlobalNPCs/GenjutsuGlobalNPC.cs:53-58 (`PuppetMovement`)
- Description: Re-read the file this run - unchanged. `FleeMovement`'s guard is still only `ControllingPlayerIndex < 0 || !Main.player[...].active`, missing the `.dead` check that `PuppetMovement`'s equivalent guard has right above it. A dead player is still `active` in Terraria (the entity persists until respawn), so a feared NPC keeps computing `away = npc.Center - deadPlayer.Center` and fleeing the fixed death location instead of resuming normal AI the way the puppet case correctly does.
- Failure scenario: A player casts `GenjutsuNightmareItem` (fear) on an enemy, then dies before the fear duration expires. The feared NPC keeps fleeing the player's death location for the rest of that window instead of returning to normal behavior.
- Suggested fix: Add `|| Main.player[ControllingPlayerIndex].dead` to `FleeMovement`'s early-return condition, matching `PuppetMovement` exactly.

## Improvements

### Performance - `AnimalMinionProjectile.FindTarget` still scans all `Main.maxNPCs` every tick per active minion (unfixed since 2026-09-23/25/26)
- Location: Content/Minions/AnimalMinionProjectile.cs:246-270 (`FindTarget`); contrast with the already-shipped fix in Content/Minions/ShadowCloneProjectile.cs:27-34,86-123
- Current: Confirmed still an unthrottled `for (i = 0; i < Main.maxNPCs; i++)` scan with no caching or rescan interval, called unconditionally from `AI()` every tick. This run additionally confirmed all 4 previously-unread leaf subclasses (BulldogHound/NinjaHound/ScoutHound/Slug) inherit it as-is with no override, so all 6 animal-summon minions share the exact same unthrottled scan, and a fully-decked-out summoner can have several active simultaneously.
- Proposed: Port the cache-and-throttle approach already shipped for `ShadowCloneProjectile.FindTarget` (cached target + periodic rescan, dropped the instant it's no longer chaseable) into the shared base class so all 6 subclasses benefit at once.
- Risk: trivial - behavior-preserving perf port of an already-verified sibling fix.

### Robustness/Performance - `HitDebugLoggerPlayer` is still an unremoved TEMP debug hook attached to every player (unfixed since 2026-09-21/24)
- Location: Common/Players/HitDebugLoggerPlayer.cs:12-38
- Current: Confirmed still present and unmodified, read in full this run. Its own header comment calls it a TEMP aid to be removed once the `TailedBeastBoss` hitbox investigation closed (it did, 2026-09-21/22); it still runs an unconditional `Main.maxNPCs` scan plus disk log writes on every hit any player takes.
- Proposed: Delete the class (its own stated removal condition is already met), or gate it behind a debug flag.
- Risk: trivial - debug-only instrumentation, zero gameplay effect either way.

### Robustness - `smoke_test_server.sh` still always exits 0 even on a detected FAIL/exception (unfixed since 2026-09-12)
- Location: tools/smoke_test_server.sh:19-35
- Current: Confirmed still present, read in full this run - the server launch line still ends in `|| true` and neither failure branch (`FAIL: server did not report a clean start` / `WARNING: exception-like text found`) is followed by `exit 1`, so the script's exit code is unconditionally 0.
- Proposed: Track whether either failure condition was hit and `exit 1` at the end so a CI/automation caller can gate on this script's exit code.
- Risk: trivial - purely additive, no change to detection logic.

### Robustness - `pixellab_generate.py`'s `edit_image` polling loop still has no timeout/max-retry cap (unfixed since 2026-08-08/2026-09-10)
- Location: tools/pixellab_generate.py:92-106
- Current: Confirmed still present, read in full this run - `while True: time.sleep(5); ...` only exits on `"completed"`/`"failed"` status; a job stuck `"pending"`/`"processing"` forever polls indefinitely with no abort path short of killing the process.
- Proposed: Track elapsed time/poll count and raise a `RuntimeError` past a max wait (e.g. 10-15 minutes).
- Risk: trivial - purely additive bound-checking, no change to the success path.
