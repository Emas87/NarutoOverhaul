# Audit report - NarutoOverhaul - 2026-09-10
1 bugs (0 high, 1 medium, 0 low), 3 improvements

## Bugs

### Medium - generate_armor_sheet.py can silently clip the bottom of a Head frame when top-anchoring into its cell
- Location: tools/generate_armor_sheet.py:162 (`HEAD_TOP_MARGIN`), :165-176 (`_center_on_canvas`), :213-214 (`build`, where `anchor="top"` is selected for `--equip-type head`)
- Description: `_center_on_canvas` computes `scale = min(canvas_w / frame.width, canvas_h / frame.height, 1.0)` so the scaled frame's height never exceeds `canvas_h` (56px) - but for the `anchor == "top"` case (Head only) it then pastes that frame at `y = HEAD_TOP_MARGIN` (10), not `y = 0`. The scale calculation never subtracts the 10px margin, so any frame whose scaled height lands in the 46-56px range (i.e. content that fills most of the 56px cell height, which is exactly what a full headband/forehead-protector-plus-hair frame is likely to do) gets pasted with its bottom `10 - (56 - frame.height)` pixels past `canvas_h`. `canvas` here is a fresh `Image.new("RGBA", (canvas_w, canvas_h), ...)` sized to exactly one 40x56 cell (not the full sheet), so `canvas.paste(frame, (x, y), frame)` silently clips anything that falls outside those bounds - Pillow raises no error and prints no warning, it just doesn't draw the part of `frame` that's out of range.
- Failure scenario: Running `build --equip-type head ...` on a sheet whose sliced-and-trimmed Head frame content is taller than 46px (very plausible - the module's own comment says real reference art like YewWoodHelmet_Head's frame 0 content bbox was already 20px tall with margin, and nano-banana-generated art is not guaranteed to trim that tight) produces a Head equip texture whose bottom edge of art is silently cut off, with no error printed and no indication in the tool's own output that anything went wrong - the exact class of bug CLAUDE.md's "CRITICAL: real armor equip-layer template shapes" note says was likely the mechanical cause of a previous "weird full-face head" defect, just from a different root cause this time (clipping instead of wrong template shape).
- Suggested fix: When `anchor == "top"`, compute `scale` against `canvas_h - HEAD_TOP_MARGIN` instead of `canvas_h` (i.e. pass the usable height, not the full cell height, into the `min()`), so a full-height frame scales down enough to fit below the margin instead of overflowing it.

## Improvements

### duplication - `outline_pass` is byte-for-byte duplicated between the two procedural sprite generators
- Location: tools/generate_boss_sprites.py:121-135 and tools/generate_town_npc_sprites.py:239-254
- Current: Both files define an identical `outline_pass(img)` function (same flood-from-alpha 1px-outline algorithm, same 4-neighbor check, same `to_outline` two-pass pattern) - only the module-level `OUTLINE` color constant they close over differs.
- Proposed: Move `outline_pass` (parameterized on the outline color) into a small shared module (e.g. `tools/pixel_sprite_common.py`) that both scripts import, so a future fix to the outlining algorithm (e.g. diagonal neighbors, or fixing the O(w*h*4) rescan) only has to happen once.
- Risk: trivial

### robustness - `extract_tmod.py` never closes the `.tmod` file handle it opens
- Location: tools/extract_tmod.py:46-71 (`parse_tmod` opens and returns `f`), :92-118 (`main`, which never calls `f.close()` on either the `list` or `extract` path, including the `sys.exit` bad-magic path inside `parse_tmod` itself)
- Current: `parse_tmod` does `f = open(path, "rb")` and hands the raw handle back to the caller for `extract_file` to `seek`/`read` from later; nothing in `main()` (or a `with`/`try/finally`) ever closes it, so every invocation of this CLI leaks one open file descriptor for the process's lifetime.
- Proposed: Use `with open(path, "rb") as f:` in `parse_tmod` (returning the read bytes/entries instead of a live handle), or at minimum add `f.close()` at the end of both branches in `main()`.
- Risk: trivial (short-lived CLI process, OS reclaims the descriptor at exit either way - flagged because the fix is free and this script's own docstring says it's also meant to be pointed at large Workshop mods, where a real bug elsewhere in a future batch/loop usage of `parse_tmod` would compound this)

### robustness - `pixellab_generate.py`'s job-polling loop has no timeout or retry cap
- Location: tools/pixellab_generate.py:92-106 (`edit_image`'s `while True: time.sleep(5); status = _get(...)`)
- Current: The loop polls the PixelLab background job forever, sleeping 5s between polls, with no maximum wait time or attempt count - the only ways out are `status == "completed"` or `status == "failed"`.
- Proposed: Add a wall-clock or iteration cap (e.g. exit with a clear error after ~10 minutes / 120 polls) so a job stuck in `"queued"`/`"running"` on the API side (or an API response that never settles into either terminal state) doesn't hang the script indefinitely with no way to tell from the output that it's stuck versus just slow.
- Risk: trivial
