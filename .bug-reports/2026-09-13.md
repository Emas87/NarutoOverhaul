# Audit report - NarutoOverhaul - 2026-09-13
2 bugs (0 high, 1 medium, 1 low), 1 improvement

## Bugs

### Medium - PainBoss's Preta Path chakra drain still has no multiplayer-client guard, contradicting the very comment that explains why it needs one
- Location: Content/NPCs/Bosses/PainBoss.cs:560-568 (`DoPreta`), called from the `AttackState` switch in `DoAttack` at :331; contrast with the guarded sibling `DoAnimal` at :529-550 and `DoAsura` at :393-406 in the same file
- Description: `DoPreta` runs `if (NPC.Distance(target.Center) <= PretaDrainRadius && StateTimer % 10 == 0) { target.GetModPlayer<ChakraPlayer>().TrySpendChakra(8f); ChakraPlayer.SendCorrection(target); ... }` with no `Main.netMode != NetmodeID.MultiplayerClient` check. Every other side-effecting `Do*` attack method in this same class guards itself this way before spawning a projectile or mutating shared state (`DoAnimal:540`, `DoAsura:399`), and `Common/Players/ChakraPlayer.cs:168-171` spells out the exact assumption this code depends on: "PainBoss's Preta Path drains chakra server-side from AI(), which only ever touches the server's own authoritative copy — without this, the client never learns their chakra was spent." That assumption is still false as written — `NPC.AI()` (and therefore `DoPreta`) runs on every connected peer's own local simulation of the boss, not just the server, which is exactly why the two sibling methods in this file need their own guards. This was already flagged in `.bug-reports/2026-09-08.md` and has not been touched since (last commit touching this file, `e1aef71`, predates that report).
- Failure scenario: In a dedicated-server or listen-server game with a bystander client present (anyone other than Pain's current target and the host), that bystander's own client-side simulation of PainBoss also executes `DoPreta` on its shadow copy of the boss and calls `TrySpendChakra` on its own shadow copy of the target player's `ChakraPlayer`. Chakra is a fully custom resource with no vanilla net-sync, and `ChakraPlayer.SendCorrection` only pushes the corrected value to the drained player's own connection (`packet.Send(player.whoAmI)`), never to bystanders — so the bystander's local Chakra shadow-copy for the drained player silently drifts and is never corrected.
- Suggested fix: Wrap the `TrySpendChakra`/`SendCorrection`/VFX block in `if (Main.netMode != NetmodeID.MultiplayerClient) { ... }`, matching `DoAnimal`/`DoAsura` immediately above/below it in the same file (the VFX call can stay outside the guard if client-local dust is intended to play everywhere, the same way `DoAnimal` keeps its own no-guard-needed effects separate from the guarded projectile spawn).

### Low - StarterItemPlayer's debug item giveaway still skips the multiplayer-client guard its sibling methods use
- Location: Common/Players/StarterItemPlayer.cs:59-96 (`OnEnterWorld` calling `GiveStarterItemsOnce`), contrast with the guarded `ForceStoryProgressUnlock`/`ForceTownNpcSpawn` at :112 and :128
- Description: `OnEnterWorld` calls three methods. `ForceStoryProgressUnlock` and `ForceTownNpcSpawn` both open with `if (Main.netMode == NetmodeID.MultiplayerClient) { return; }`, but `GiveStarterItemsOnce` — which writes six items straight into `Player.inventory` via `GiveItem` — has no such guard. This is the same gap flagged in `.bug-reports/2026-09-08.md`; the method has grown (now also hands out the four Taijutsu kick items, Genjutsu Nightmare, and Susanoo as TEMP testing scaffolding) but the missing guard was not part of any of those edits.
- Failure scenario: On a client joining a dedicated-server multiplayer game, `GiveStarterItemsOnce` runs and mutates that client's own local `Player.inventory` array directly with no accompanying network message — a raw slot assignment doesn't trigger tModLoader/vanilla's normal item-sync packets the way picking up or crafting an item does. The two guarded sibling methods in the same class treat "don't do inventory/world-state-changing work as a plain MultiplayerClient" as the rule for this exact file; this method being the odd one out looks like an oversight, not a deliberate exception, and risks the granted items being invisible to the server/other players until some unrelated action forces a sync.
- Suggested fix: Add the same `if (Main.netMode == NetmodeID.MultiplayerClient) return;` guard used by `ForceTownNpcSpawn`/`ForceStoryProgressUnlock` at the top of `GiveStarterItemsOnce` (or `OnEnterWorld` itself, ahead of all three calls, since all three now share the same requirement).

## Improvements

### duplication - the 4 Taijutsu/Genjutsu "blast VFX" items repeat the same UseAnimation shape (impact flash + player-anchored blast + dash nudge)
- Location: Content/Items/Weapons/Jutsu/IronLegItem.cs:58-69, FrontLotusItem.cs:61-74, LeafHurricaneItem.cs:57-74, GentleFistItem.cs:58-74
- Current: Each item's `UseAnimation` follows the identical shape introduced by the Taijutsu blast VFX rework (`65a9fd0`): one or two `ChakraVFX.SpawnImpactBurst` calls at a per-item offset/scale, one `ChakraVFX.SpawnPlayerAnchoredBurst<TBlast>(player, offset)` call, then `if (player.whoAmI == Main.myPlayer) { player.velocity.X = player.direction * OnUseDashSpeed; }`. Only the burst type parameter, offsets, scales, and `OnUseDashSpeed` value differ between the four. This sits alongside the already-tracked `CanUseItem`/`Shoot`/tooltip duplication across `IronLegItem`/`FrontLotusItem`/`LeafHurricaneItem` (`.bug-reports/2026-09-11.md`'s "duplication" improvement, proposing a shared `TaijutsuKickItem` base) — that finding didn't cover `UseAnimation`, and `GentleFistItem` (no `Shoot` override, since it deals damage via its own melee hitbox rather than a projectile) wasn't in scope for that proposal at all, but shares this exact same VFX/dash block.
- Proposed: If/when the previously-proposed shared base class is built, fold this `UseAnimation` shape into it too (e.g. a `virtual PlayVFXAndDash(Player)` driven by abstract `BlastProjectileType`, per-item offset/scale, and `OnUseDashSpeed`), and consider whether `GentleFistItem` can share it as a sibling even without a `Shoot` override, since the duplicated part is entirely in `UseAnimation`, not `Shoot`.
- Risk: trivial (pure refactor of 4 files, no behavior change) — same reviewed-and-deliberately-deferred status as the sibling finding: worth doing as its own pass, not a drive-by change, since a content mod with no automated combat/VFX tests makes any multi-file behavior-preservation refactor worth doing carefully rather than folded into an unrelated commit.
