## Bugs

### High - GentleFistItem spends Stamina twice per swing because its UseAnimation override and the shared TaijutsuKickItemBase.UseAnimation it calls into both independently call TrySpendStamina
- Location: Content/Items/Weapons/Jutsu/GentleFistItem.cs:61-71 (`UseAnimation`: spends stamina at :63, then unconditionally calls `base.UseAnimation(player)` at :70); Content/Items/Weapons/Jutsu/TaijutsuKickItemBase.cs:44-56 (`UseAnimation`: spends stamina again at :46) - the double call was introduced by yesterday's fix in commit 479132d ("Fix stamina double-spend..."), which added a `TrySpendStamina` call directly into the shared base's `UseAnimation` without accounting for `GentleFistItem`'s own override that already spends stamina before delegating to `base.UseAnimation()`
- Description: Before 479132d, `TaijutsuKickItemBase.UseAnimation` only played VFX/dash (no stamina spend at all - stamina was spent in `Shoot()`), so `GentleFistItem.UseAnimation` spending stamina itself and then calling `base.UseAnimation()` for the VFX/dash was correct (GentleFist has no `Item.shoot`, so `Shoot()` never fires for it - see the class comment on TaijutsuKickItemBase.cs:14-15). Yesterday's fix moved the stamina spend from `Shoot()` into the base's own `UseAnimation` (correct for `IronLegItem`/`FrontLotusItem`/`LeafHurricaneItem`, none of which override `UseAnimation`), but `GentleFistItem` still has its own `TrySpendStamina(StaminaCost)` call before it, and its override never became purely a VFX/dash delegate - it still pays the cost itself and *then* calls into a base method that now pays the same cost again. Both calls act on the same `Player.GetModPlayer<StaminaPlayer>()` instance for the same real gameplay `UseAnimation` invocation (called once per swing, not per tick - matching how the originally-reported "played VFX unconditionally" bug was described and fixed for the sibling classes), so a single Gentle Fist swing now costs `2 * StaminaCost` (16, not the declared/tooltipped 8) Stamina whenever it fully succeeds.
- Failure scenario: 1) Normal case - a player using Gentle Fist (`CanUseItem` only checks `Stamina >= StaminaCost` = 8, and the tooltip via `ModifyTooltips` in the base's sibling pattern also advertises 8) is silently charged 16 Stamina per swing, halving Gentle Fist's real attack economy versus its displayed/intended cost and versus every other Taijutsu weapon's single-spend behavior. 2) Partial-stamina case - with Stamina between 8 and 16 (e.g. 10), `CanUseItem` passes and `GentleFistItem.UseAnimation`'s own `TrySpendStamina(8)` succeeds (Stamina now 2, `_staminaSpent` in `GentleFistItem` set true so `ModifyHitNPC`/`OnHitNPC` will apply armor-pen/impact VFX), but the delegated `base.UseAnimation`'s own second `TrySpendStamina(8)` then fails (2 < 8): the base's own private `_staminaSpent` gate blocks `PlayImpactFlash`/`PlayBlast`/`ApplyDash`, so the swing plays no blast VFX and no forward dash even though the player already paid stamina and the melee hit will still land with full armor-penetration bonus - a partially-broken, visually-silent swing.
- Suggested fix: Remove the stamina spend from `GentleFistItem.UseAnimation` (Content/Items/Weapons/Jutsu/GentleFistItem.cs:61-71) and let it rely entirely on the (now stamina-spending) `base.UseAnimation()`, reading the base's own `_staminaSpent` result instead of keeping a separate field - e.g. give `TaijutsuKickItemBase` a `protected bool StaminaSpent { get; private set; }` (or similarly expose the private field) that `GentleFistItem.ModifyHitNPC`/`OnHitNPC` read directly, and delete `GentleFistItem`'s own redundant `TrySpendStamina` call and private `_staminaSpent` field. This restores a single spend per swing while keeping the "gate armor-pen/VFX on a successful spend" behavior the comment at GentleFistItem.cs:28-30 describes.
> Needs a decision: whether to expose the base's stamina-spent result via a protected property/field (minimal diff) or refactor `GentleFistItem` to stop overriding `UseAnimation` entirely and instead override a narrower hook (e.g. a new `protected virtual void OnStaminaSpent(Player player)` called from the base only after a successful spend) - the latter is a slightly larger but cleaner fix that also prevents this same class of double-call mistake for any future `TaijutsuKickItemBase` subclass that needs post-spend, pre-VFX behavior.
