# Audit report - NarutoOverhaul - 2026-09-19
3 bugs (1 high, 2 medium, 0 low), 0 improvements

## Bugs

### High - GentleFistItem still spends Stamina twice per swing (carried over from 2026-09-18, unfixed)
- Location: Content/Items/Weapons/Jutsu/GentleFistItem.cs:61-71 (`UseAnimation`: spends stamina at :63, then unconditionally calls `base.UseAnimation(player)` at :70); Content/Items/Weapons/Jutsu/TaijutsuKickItemBase.cs:44-56 (`UseAnimation`: spends stamina again at :46)
- Description: This is the exact bug reported in `.bug-reports/2026-09-18.md` ("GentleFistItem spends Stamina twice per swing"). Verified against the current tree: it is still present. Per `.bug-reports/NEEDS-INPUT.md`, a fix was written and reviewed locally by the fixer routine but discarded (`git reset --hard`) because this repo has no build/test runner available in the cloud environment to verify it, and no commit since then has landed a fix. `GentleFistItem.UseAnimation` still calls `TrySpendStamina(StaminaCost)` itself and then unconditionally delegates to `base.UseAnimation(player)`, which (since the 2026-09-16 fix in commit 479132d moved the stamina spend into the shared base for the other 3 Taijutsu kick items) now *also* calls `TrySpendStamina(StaminaCost)` on the same `StaminaPlayer` instance for the same swing.
- Failure scenario: A player using Gentle Fist (`CanUseItem` only requires `Stamina >= StaminaCost` = 8, and the tooltip advertises 8) is silently charged 16 Stamina per successful swing - double the declared/intended cost, and inconsistent with every sibling Taijutsu weapon (which spend once). With Stamina between 8 and 16 (e.g. 10), the item's own `TrySpendStamina(8)` succeeds (armor-pen/on-hit VFX get gated on, since `_staminaSpent` is set), Stamina drops to 2, and the delegated `base.UseAnimation`'s own `TrySpendStamina(8)` then fails - so the swing plays no blast VFX/dash (the base's private `_staminaSpent` gate blocks `PlayImpactFlash`/`PlayBlast`/`ApplyDash`) even though the player already paid stamina and the melee hit still lands with full armor-penetration.
- Suggested fix: Same as previously proposed - remove the stamina spend from `GentleFistItem.UseAnimation` and let it rely entirely on `base.UseAnimation()`'s single spend, exposing the base's spend result (e.g. `protected bool StaminaSpent { get; private set; }`) for `GentleFistItem.ModifyHitNPC`/`OnHitNPC` to read instead of its own private `_staminaSpent` field.
> Needs a decision: same open question as 2026-09-18 - expose the base's spend result via a protected property/field (minimal diff, the fixer routine's own preference), or give `TaijutsuKickItemBase` a narrower `protected virtual void OnStaminaSpent(Player player)` hook that `GentleFistItem` overrides instead of `UseAnimation` itself. Given this fix has now been independently rewritten and discarded twice for lack of a verifiable build environment, also worth deciding whether to just add a minimal headless build/compile check to this repo's cloud environment so straightforward one-file fixes like this one stop bouncing.

### Medium - GenjutsuNightmareItem plays its cast VFX even when the Chakra spend fails
- Location: Content/Items/Weapons/Jutsu/GenjutsuNightmareItem.cs:50-58 (`UseAnimation`)
- Description: `UseAnimation` calls `chakraSpent = player.GetModPlayer<ChakraPlayer>().TrySpendChakra(ChakraCost);` and then, regardless of the result, unconditionally spawns `ChakraVFX.SpawnBurstEffect<GenjutsuBurstProjectile>(player.Center, 1.2f)` and `ChakraVFX.SpawnPlayerAnchoredBurst<GenjutsuNightmareBlastProjectile>(player, Vector2.Zero)`. The class's own comment explains *why* a `chakraSpent` flag exists at all ("UseAnimation can't abort the swing outright... keeps a failed spend from applying the effect for free") and correctly gates the real payoff (`OnHitNPC`'s fear debuff + hit VFX) on it - but the flag is never checked before playing the initial cast VFX, so a failed spend still gets the full "I just cast Genjutsu Nightmare" visual (eye-rift blast + burst) with no Chakra actually consumed. This is the same class of bug already fixed for the Taijutsu kick items in commit 479132d ("played dash/VFX even when [the] independent stamina roll failed"), left unfixed here since `GenjutsuNightmareItem` predates that fix and wasn't touched by it.
- Failure scenario: `CanUseItem` only checks Chakra once, when the swing begins; Chakra is not static afterward - `TransformationPlayer.PostUpdateMiscEffects` drains Chakra every tick while a Chakra-costing Transformation Form (Sage Mode, Tailed Beast Mode, Curse Mark, etc.) is active, independent of item-use timing (the exact race already documented for Rasengan/Gentle Fist in `.bug-reports/2026-09-11.md`, and fixed there). A player with an active draining form and Chakra sitting just above 20 can have the per-tick drain land between `CanUseItem` and `UseAnimation`, making `TrySpendChakra` fail - the player pays nothing, but still sees and hears the full cast effect, misleadingly signaling a successful cast even though no fear debuff will land on hit.
- Suggested fix: Move both `ChakraVFX.SpawnBurstEffect<GenjutsuBurstProjectile>` and `ChakraVFX.SpawnPlayerAnchoredBurst<GenjutsuNightmareBlastProjectile>` inside an `if (chakraSpent)` block (or `return` early when `!chakraSpent`), matching the pattern `TaijutsuKickItemBase.UseAnimation` now uses.

### Medium - Hiraishin seals planted by MinatoKunaiProjectile never register with the server's authoritative mark registry when thrown by a non-host multiplayer client
- Location: Content/Projectiles/MinatoKunaiProjectile.cs:102-124 (`PlantSeal`); Common/Systems/HiraishinMarkerSystem.cs:93-118 (`AddMark`/`SyncToClients`)
- Description: `PlantSeal` only runs its placement branch `if (Projectile.owner == Main.myPlayer)` - i.e. on the client that owns the projectile, which in multiplayer can be a non-host client. On that client it calls `WorldGen.PlaceObject` (which locally invokes `HiraishinSealTile.PlaceInWorld` -> `HiraishinMarkerSystem.AddMark`), then manually calls `NetMessage.SendTileSquare(-1, tileCoord.X, tileCoord.Y, 1)` to replicate the tile to other clients. `HiraishinMarkerSystem.AddMark`'s own `SyncToClients()` only broadcasts `WorldData` `if (Main.netMode == NetmodeID.Server)` - true on the server, false on every regular client - so on a non-host client the mod's own mark-registry sync never fires; only the raw tile-square packet goes out. A `SendTileSquare`/`TileSendSquare` packet received by the server patches the tile array directly (the same low-level path vanilla uses for client tile edits) and does not invoke `WorldGen.PlaceObject`/`ModTile.PlaceInWorld`, so the server's own `HiraishinMarkerSystem.MarkedTiles` (the single source of truth the class's own header comment describes, replicated to clients via `NetSend`/`NeReceive` on join and on every `AddMark`/`RemoveMark`) never learns about this seal. The class comment on `HiraishinSealTile.PlaceInWorld` even calls the explicit `AddMark` in `MinatoKunaiProjectile` "belt-and-suspenders (idempotent)", but it is not redundant in this one case - it's the only `AddMark` call that happens, and it happens on the wrong machine.
- Failure scenario: In a multiplayer session, a non-host client uses the Hiraishin Kunai and it embeds in a wall. The seal tile visually appears for everyone (the tile square packet places it). The throwing client can warp to it locally for a while (their own in-memory `MarkedTiles` has it), but no other player's warp list ever includes it, and the very next time the server broadcasts `WorldData` for any reason (another player adding/removing a mark elsewhere, or a fresh player joining) the throwing client's own local list is overwritten by the server's (still-missing-this-seal) list, silently un-warping it for the placer too - leaving a permanent, physically-visible, but functionally dead seal, and defeating the entire point of the mod's "shared warp network any player can use" design for exactly the players who most need remote placement (non-host clients).
- Suggested fix: Either route Hiraishin-Kunai placement through the server (e.g. only the server actually calls `WorldGen.PlaceObject`/`AddMark`, driven by an explicit mod packet from the owning client carrying the target tile coordinate, mirroring how `TransformationPlayer`/`ChakraPlayer` sync state today), or make `HiraishinMarkerSystem.AddMark` itself request a server-side add (send a small mod packet to the server saying "please AddMark(tile)") instead of assuming the calling client's own `AddMark` call is authoritative. A client-only "trust the tile square" approach does not work here because `SendTileSquare` never invokes `PlaceInWorld` on the receiving end.
> Needs a decision: whether to fix this by adding a dedicated `AddMark` network packet (small, consistent with how the mod already syncs Chakra/Stamina/Transformation state) or by making the kunai's owning client defer to `Projectile.owner == Main.myPlayer && Main.netMode != NetmodeID.MultiplayerClient` for the actual placement and instead have the *server* place the seal once it receives the projectile's tile-collide event (requires the projectile's `OnTileCollide`/AI to run its placement logic authoritatively server-side rather than client-side).
