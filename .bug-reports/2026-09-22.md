## Bugs

### High - TransformationPlayer's SyncTransformation packet handler assigns attacker-controlled form-index/gate-level values with no range validation, crashing every client (and the server) that next runs that player's ResetEffects/PostUpdateMiscEffects
- Location: Common/Players/TransformationPlayer.cs:393-417 (`HandlePacket`), consumed unguarded at line 255 (`ResetEffects`) and line 306 (`PostUpdateMiscEffects`); `TransformationSystem.RegisteredForms` is a fixed 8-entry list (Common/Systems/TransformationSystem.cs:21-32)
- Description: `HandlePacket` reads `activeFormIndex` as a raw `sbyte` (-128..127) and `eightGatesLevel` as a raw `byte` (0..255) straight off the wire and assigns them directly to `TransformationPlayer.ActiveFormIndex`/`EightGatesLevel` with zero bounds checking - only `-1` (no form) is ever special-cased. `c6bbd3e` ("Fix network packet spoofing") specifically hardened this exact handler against a spoofed write-target (`playerIndex` vs. real `whoAmI`), but never touched the payload's *values*, which are just as attacker-controlled as the index it fixed. Every other place `ActiveFormIndex` gets set goes through `ToggleForm`, which explicitly bounds-checks it (`if (formIndex < 0 || formIndex >= TransformationSystem.RegisteredForms.Count) return;`) before ever touching `RegisteredForms[formIndex]` - `HandlePacket` is the one path that skips that check entirely, even though it feeds the same field the same way.
- Failure scenario: A modified client sends a `SyncTransformation` packet with `activeFormIndex` set to anything outside `[-1, 7]` (e.g. 8, -5, 100). On the server (`Main.netMode == NetmodeID.Server` branch of `HandlePacket`), `ActiveFormIndex` is set to that value with `whoAmI` correctly used as the write target (so the spoofing fix's own protection doesn't stop this). On the very next tick, the server's own simulated instance of that player runs `ResetEffects`, which unconditionally executes `TransformationForm form = TransformationSystem.RegisteredForms[ActiveFormIndex];` - an `ArgumentOutOfRangeException` on a `List<T>` indexer for any value outside `0..7`. Because `HandlePacket` also relays the same unvalidated value to every other connected client (`relay.Write((sbyte)activeFormIndex)`), and each of those clients runs the identical `ResetEffects`/`PostUpdateMiscEffects` hooks for their own copy of *every* player (needed so `SageModeDrawLayer` and CC/life-drain forms render/apply correctly for everyone), the same exception fires on every connected client's next frame too - one malformed packet from one player takes down the whole session, not just the sender. `EightGatesLevel` has the same gap (no clamp to `0..8`): a bogus value doesn't crash by itself, but flows straight into `EightGatesForm.ApplyStatBoosts`/`LifeDrainPerTick` (`0.2f * level`, `0.15f * level`, `2 * level`, `1.5f * level`) and can hand a player wildly out-of-design stat swings.
- Suggested fix: In `HandlePacket`, before assigning, clamp `activeFormIndex` to `-1` or `[0, TransformationSystem.RegisteredForms.Count - 1]` (drop/ignore the packet, or coerce to `-1`, on anything else) and clamp `eightGatesLevel` to `[0, 8]` - mirroring the same bounds check `ToggleForm` already applies to every other write path for this field.

## Improvements

### Duplication - all four town NPCs duplicate ~110 lines of identical frame-animation/chat-bubble/facing logic verbatim
- Location: Content/NPCs/Town/GuySenseiNPC.cs:89-160, Content/NPCs/Town/ItachiNPC.cs (same block), Content/NPCs/Town/KakashiNPC.cs:89-160, Content/NPCs/Town/ShinobiVendorNPC.cs:92-160
- Current: `FindFrame` (idle/walk debounce + frame stepping), `ChatBubblePosition` (Y offset + mirrored X + flipped `SpriteEffects` for the inverted facing convention), and `PostAI` (velocity-driven `direction`/`spriteDirection`) are copy-pasted character-for-character across all four `ModNPC` classes, with only the per-NPC frame-count constants (`IdleFrameCount`/`WalkFrameCount`) and `ChatBubbleYOffset`/`SizeMultiplier` differing (and those two constants are themselves identical `34f`/`1.5f` in every file).
- Proposed: Factor the shared block into a common base class (e.g. `NarutoTownNpc : ModNPC`) or a small shared helper struct that each NPC configures with its own frame counts, keeping only `SetDefaults`/`GetChat`/`AddShops` (the genuinely NPC-specific parts) in each subclass. This is pure animation/UI plumbing, not gameplay-affecting, so there's no balance risk - the value is maintainability: a future fix to the debounce logic or the bubble-mirroring math (both non-obvious, comment-heavy workarounds) currently has to be copied into four files by hand, and it would be easy to update three and miss the fourth.
- Risk: trivial - a straight refactor extraction with no behavior change; can be verified by comparing frame timings/bubble placement before and after in a local build.
