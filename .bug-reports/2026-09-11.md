# Audit report - NarutoOverhaul - 2026-09-11
2 bugs (0 high, 1 medium, 1 low), 2 improvements

## Bugs

### Medium - Rasengan and Gentle Fist can fire/land for free because their resource-spend's success is never checked
- Location: Content/Items/Weapons/Jutsu/RasenganItem.cs:40-44 (`Shoot`), Content/Items/Weapons/Jutsu/GentleFistItem.cs:53-65 (`UseAnimation`) and :67-76 (`ModifyHitNPC`/`OnHitNPC`, which apply unconditionally); root cause enabled by Common/Players/TransformationPlayer.cs:292-319 (`PostUpdateMiscEffects`, the per-tick Chakra drain for active Transformation Forms)
- Description: Every other Chakra/Stamina-gated Jutsu item in this same directory follows one of two safe patterns: gate the projectile spawn on the spend's result (`if (!player.GetModPlayer<ChakraPlayer>().TrySpendChakra(ChakraCost)) { return false; }` - used by `AllKillingAshBonesItem`, `ChidoriItem`, `FireballItem`, `GenjutsuIllusionItem`, `GenjutsuSleepItem`, `GreatBreakthroughItem`, `ShadowCloneItem`, `ShinraTenseiItem`, `SusanooItem`, `WaterDragonItem`, and `IronLegItem`/`FrontLotusItem`/`LeafHurricaneItem` via `return player.GetModPlayer<StaminaPlayer>().TrySpendStamina(StaminaCost);`), or capture the result in a flag and gate the payoff on it (`GenjutsuNightmareItem`'s `chakraSpent`, with its own comment explaining exactly why: "UseAnimation can't abort the swing outright... keeps a failed spend from applying the effect for free"). `RasenganItem.Shoot()` calls `player.GetModPlayer<ChakraPlayer>().TrySpendChakra(ChakraCost);` and discards the bool, then unconditionally `return true;` (the projectile always spawns). `GentleFistItem.UseAnimation()` calls `player.GetModPlayer<StaminaPlayer>().TrySpendStamina(StaminaCost);`, also discards the bool, and unlike Genjutsu Nightmare has no flag at all gating its `ModifyHitNPC`/`OnHitNPC` (40 armor penetration + on-hit VFX apply regardless).
  `CanUseItem` (checked once, when the swing begins) makes this look safe at a glance, but Chakra is not static between that check and the later spend: `TransformationPlayer.PostUpdateMiscEffects` calls `chakraPlayer.TrySpendChakra(form.ChakraDrainPerTick)` on **every single game tick** while any Chakra-costing Transformation Form (Sage Mode, Tailed Beast Mode, Curse Mark, etc.) is active - completely independent of item-use timing. Any player casting Rasengan (or any Chakra ability) while such a form is active, with Chakra sitting between `ChakraCost` and `ChakraCost + ChakraDrainPerTick`, can have `CanUseItem` observe a still-sufficient value on one tick and the per-tick transformation drain push Chakra below cost by the tick `Shoot()` actually runs - `TrySpendChakra` then legitimately fails (spends nothing) but `RasenganItem.Shoot()` returns `true` anyway.
- Failure scenario: Player has an active Chakra-draining Transformation Form up and Chakra sitting just above Rasengan's 20-Chakra cost. On the tick the per-tick form drain lands between Rasengan's `CanUseItem` check and its `Shoot()` call, `TrySpendChakra` returns `false` (nothing spent) but the projectile fires anyway with its full 45 damage - a free Rasengan. The same shape applies to Gentle Fist with Stamina (Stamina has no continuous per-tick drain from a Transformation Form today, but `StaminaPlayer`'s own file comments that a server-side drain mechanism "for whenever one is added" is already anticipated, and Gentle Fist's `TrySpendStamina` result is discarded exactly like Rasengan's regardless).
- Suggested fix: Match the established sibling convention - either gate `RasenganItem.Shoot()` on the spend (`return player.GetModPlayer<ChakraPlayer>().TrySpendChakra(ChakraCost);` instead of an unconditional `return true`), or capture the bool and skip the payoff the way `GenjutsuNightmareItem` does with `chakraSpent`. For `GentleFistItem`, capture `TrySpendStamina`'s return in a field (same `chakraSpent`-style pattern) and gate `ModifyHitNPC`/`OnHitNPC`'s bonuses on it.

### Low - slice_fx_sheet.py crashes with a raw ValueError instead of a clear error when `row_margin` doesn't fit the row height
- Location: tools/slice_fx_sheet.py:75-84 (`slice_sheet`'s `y0`/`y1` computation) and :95 (`ap.add_argument("--row-margin", ...)`, unvalidated)
- Description: `slice_sheet` computes `y0 = i * src_row_h + row_margin` and `y1 = (i + 1) * src_row_h - row_margin` where `src_row_h = sheet.height // rows`, then does `sheet.crop((0, y0, sheet.width, y1))`. Nothing checks that `row_margin < src_row_h / 2`. Verified directly: `Image.crop()` raises `ValueError: Coordinate 'lower' is less than 'upper'` (not a silent bad output) whenever `y1 <= y0`, i.e. whenever `2 * row_margin >= src_row_h`.
- Failure scenario: Running the tool with a sheet that has many rows relative to its height, or an explicitly larger `--row-margin` (both plausible - the tool's own default `ROW_MARGIN = 10` was tuned for the handful of 6-row VFX sheets landed so far, per its own comment; a future thinner-row sheet, e.g. a 10+ frame animation packed into the same canvas height, would hit this), crashes with a bare Python traceback pointing into Pillow internals instead of a message that says "increase frame_h / decrease rows / lower --row-margin for this sheet."
- Suggested fix: After computing `src_row_h`, assert/validate `row_margin * 2 < src_row_h` and exit with a clear message (`f"--row-margin {row_margin} too large for {rows} rows in a {sheet.height}px-tall sheet (row height {src_row_h}px)"`) before attempting the crop.

## Improvements

### duplication - IronLegItem/FrontLotusItem/LeafHurricaneItem repeat the same CanUseItem/Shoot/tooltip boilerplate three times
- Location: Content/Items/Weapons/Jutsu/IronLegItem.cs:49-53,71-80, FrontLotusItem.cs:51-55,76-86, LeafHurricaneItem.cs:47-51,76-85
- Current: All three kick items independently redeclare an identical-shaped `CanUseItem` (`StoryProgressSystem.Downed* && player.GetModPlayer<StaminaPlayer>().Stamina >= StaminaCost`), an identical-shaped `Shoot` (`return player.GetModPlayer<StaminaPlayer>().TrySpendStamina(StaminaCost);`), and near-identical `ModifyTooltips` (a `StaminaCost` line + a `StoryRequirement` line). Only the story-progress flag, `StaminaCost` value, and (for Front Lotus) an extra armor-pen tooltip line differ. `TaijutsuKickProjectile` already extracts the equivalent shared shape on the projectile side of these same three weapons (see its own header comment) - the Item side never got the same treatment.
- Proposed: Pull the shared `CanUseItem`/`Shoot`/base-tooltip logic into an abstract `TaijutsuKickItem : ModItem` (parallel to `TaijutsuKickProjectile`) exposing `abstract float StaminaCost`, `abstract bool StoryGate(Player)` (or a `Func<bool>`), and a `virtual` tooltip hook for the Front-Lotus-only armor-pen line - each concrete item then only supplies its own `SetDefaults`/`UseAnimation`.
- Risk: trivial (pure refactor of 3 files with no behavior change; would also be the natural place to fix the Medium bug above for these 3 items if the fix is applied here instead of per-file)

### robustness - extract_tmod.py's 7-bit string reader raises a bare IndexError on a truncated/corrupt .tmod
- Location: tools/extract_tmod.py:34-43 (`_read_7bit_string`)
- Current: `b = f.read(1)[0]` indexes directly into the bytes returned by `f.read(1)` with no length check; at EOF, `f.read(1)` returns `b""`, and `b""[0]` raises `IndexError: index out of range` with no context about which field or file offset failed.
- Proposed: Check `if not chunk: raise ValueError(f"Unexpected EOF reading 7-bit-encoded string at offset {f.tell()}")` before indexing, so a truncated/corrupted `.tmod` (e.g. a partial Workshop download) fails with a message that says what went wrong instead of a bare traceback three frames into decode logic.
- Risk: trivial
