## Improvements

### Maintainability - mirrored scroll-bonus constant can silently drift from its source of truth
- Location: `Common/Players/ChakraPlayer.cs:166` (`NumberedChakraScrollItemIncreasePerScroll = 20f`)
  and `Common/Players/StaminaPlayer.cs:179` (`NumberedStaminaScrollItemIncreasePerScroll = 20f`),
  each a private copy of `Content/Items/Consumables/NumberedChakraScrollItem.cs:17`
  (`ChakraIncreasePerScroll = 20f`) and
  `Content/Items/Consumables/NumberedStaminaScrollItem.cs:17` (`StaminaIncreasePerScroll = 20f`)
  respectively.
- Current: `ChakraPlayer.LoadData`/`StaminaPlayer.LoadData` reconstruct
  `BaseMaxChakra`/`BaseMaxStamina` from `ConsumedChakraScrolls`/
  `ConsumedStaminaScrolls` on a legacy/corrupt save
  (`BaseMaxChakra <= 0f`), using a private constant the comment admits is
  "kept as a local constant mirroring that item's [...]IncreasePerScroll"
  because referencing the item class directly would create a circular,
  load-order-sensitive reference. Both pairs currently agree (20f/20f), so
  there is no live bug, but nothing enforces that agreement: if either
  scroll's `...IncreasePerScroll` is ever tuned (a balance pass bumping it
  to, say, 25f) without updating the matching private constant in the
  player class, every subsequent legacy-save reconstruction would compute
  the wrong `BaseMaxChakra`/`BaseMaxStamina` for a player partway through
  the 7-scroll sequence, silently and with no test or compiler error to
  catch it.
- Proposed: move the shared value to one place both sides can reference
  without a circular/load-order dependency - e.g. a small static class with
  no dependency on either `ModItem` or `ModPlayer` (both already sit in the
  `NarutoOverhaul` assembly, so a plain `internal static class
  ScrollBonusConstants { public const float ChakraPerScroll = 20f; public
  const float StaminaPerScroll = 20f; }` in `Common/` would work), and have
  both the item bases and the player classes read from it. Alternatively,
  add a build-time or startup assertion that the two values match so any
  future drift fails loudly instead of silently.
- Risk: trivial - a pure refactor with no behavior change (both current
  values already agree), touching 4 files.
