## Bugs
### Low - PaperBombProjectile can latch onto an unrelated NPC that reuses the dead target's slot
- Location: `Content/Projectiles/PaperBombProjectile.cs:24-25` (fields),
  `:47-59` (`AI()`'s `Stuck` branch), `:112-125` (`OnHitNPC`)
- Description: when the bomb sticks to an NPC on hit, it remembers only a raw
  `int stuckNpcIndex = target.whoAmI` and a fixed offset, then every tick does
  `NPC npc = Main.npc[stuckNpcIndex]; if (!npc.active) Explode(); else
  Projectile.position = npc.Center + stuckOffsetFromNpcCenter - ...`. Terraria
  reuses a dead NPC's array slot for the next NPC that spawns (vanilla natural
  spawning and this mod's own summons - e.g. `SlugMinionBuff`/
  `NinjaHoundMinionBuff` minions dying and respawning - run in the same update
  order as projectile AI). If a new, unrelated NPC is assigned that exact index
  in the same tick the original dies (before `PaperBombProjectile.AI()` runs
  that tick), `npc.active` reads `true` for the new NPC and the bomb silently
  starts riding it instead of exploding in place.
- Failure scenario: a paper bomb stuck to a dying jungle-camp-style minion (or
  any NPC killed the instant a different NPC spawns into the same slot, which
  is most likely during a fight with lots of spawn/despawn churn - e.g. a
  Taijutsu/Ninjutsu summon fight or a busy boss arena) visibly teleports to
  and then detonates on a completely unrelated NPC the player never hit with
  this bomb, instead of harmlessly fizzling at the spot where its real target
  died. Worst case is a stray explosion in an unexpected place; there is no
  crash, no player damage, and no exploit (the projectile is already
  `friendly`-only), so the practical impact is a visual/placement oddity, not
  a safety issue.
- Suggested fix: when `!npc.active`, also explode immediately on the following
  tick regardless (already done) - the remaining gap is only the same-tick
  race before that check runs. Closing it fully means also validating the
  slot's identity before trusting it, e.g. cache `target.type` alongside
  `stuckNpcIndex` and additionally require `npc.type == stuckNpcType` before
  riding along (falling back to `Explode()` on a mismatch), the same guard
  `KaguyaBlessingBoltProjectile.AI()` effectively gets for free from its
  `IsMoonLordPart` type filter. This is the only projectile in the codebase
  that holds an NPC index across multiple `AI()` ticks without such a check.
  > Needs a decision: is this worth guarding given how narrow the window is
  > (one tick, and only when something else spawns into the exact freed slot
  > before the bomb's own `AI()` runs), or is the current "explode on
  > `!active`" check close enough given the benign worst case? A type-check
  > guard is a few lines and does not change normal behavior either way.
