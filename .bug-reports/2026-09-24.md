## Bugs

### Medium - `NarutoOverhaulConfig.EnableSoftBossScaling` is `ClientSide`-scoped but drives a server-authoritative effect, so it silently does nothing for non-host players
- Location: Common/Systems/NarutoOverhaulConfig.cs:9-17 (declares `Mode => ConfigScope.ClientSide` and the flag, with a comment claiming "nothing here affects gameplay balance in a way that needs to be server-authoritative... the boss scaling toggle only affects the reading client's own local experience"); read at Content/NPCs/Bosses/OrochimaruBoss.cs:199 and Content/NPCs/Bosses/KaguyaBoss.cs:187, both inside `OnSpawn`
- Description: `EnableSoftBossScaling` is read inside each boss's `OnSpawn`, which (per the standard tModLoader boss-summon pattern used by every summon item in this mod, and confirmed by these same two files needing their own `SendExtraAI`/`ReceiveExtraAI` just to push the resulting `lifeMax` to clients - see OrochimaruBoss.cs:212-220, KaguyaBoss.cs:198-210) only actually executes on whichever machine calls `NPC.NewNPC` - the server in dedicated/host-and-play multiplayer, not each connecting client. The resulting `NPC.lifeMax`/`damage`/`defense` scaling is then broadcast to every player via the normal NPC sync + this mod's own extra-AI packet, i.e. it is inherently one shared, global decision for the whole session - the opposite of what `ConfigScope.ClientSide` is for (a per-machine value that only affects that machine's own local behavior). The doc comment's own justification is directly contradicted by the very SendExtraAI code sitting a few lines below it in each boss file.
- Failure scenario: A non-host player on a dedicated server (or a joining client in a "Host & Play" session) opens their own mod config and disables `EnableSoftBossScaling` expecting an easier Orochimaru/Kaguya fight for themselves. Nothing changes - the server process's own (or the host's own) copy of this ClientSide config is the one actually read in `OnSpawn`, so scaling is applied or not for literally every player in the session based on that one machine's setting, regardless of what any other player configured. On a truly headless dedicated server binary this option effectively can't be tuned via the normal in-client UI at all for the people playing on it.
- Suggested fix: Change `Mode` to `ConfigScope.ServerSide` (tModLoader syncs a ServerSide config's authoritative value down to every client, so `OnSpawn` reading it - wherever it runs - gets one consistent, session-wide value, matching what the code is actually doing) and correct the misleading comment. If a genuinely per-player difficulty toggle is wanted instead, that needs a different mechanism entirely (e.g. scaling computed per-nearby-player rather than baked into a single shared `NPC.lifeMax` at spawn), which is a larger design change.
> Needs a decision: whether `EnableSoftBossScaling` should become one shared `ServerSide` setting for the whole session (small, mechanical fix - just change the scope + comment), or be redesigned as genuine per-player scaling (bigger change, touches how boss stats are computed and synced).

### Low - `GenjutsuGlobalNPC.FleeMovement` keeps fleeing a caster who has since died, unlike the parity check in `PuppetMovement`
- Location: Common/GlobalNPCs/GenjutsuGlobalNPC.cs:53-58 (`PuppetMovement`, checks `.dead`) vs Common/GlobalNPCs/GenjutsuGlobalNPC.cs:77-91 (`FleeMovement`, does not)
- Description: `PuppetMovement`'s guard is `ControllingPlayerIndex < 0 || !Main.player[...].active || Main.player[...].dead` - if the controlling player dies, it falls through to `return true` and lets the NPC's normal AI resume. `FleeMovement`'s guard is only `ControllingPlayerIndex < 0 || !Main.player[...].active` - a dead player is still `active` in Terraria (their entity persists until respawn), so this check passes and `FleeMovement` goes on to compute `away = npc.Center - deadPlayer.Center` and keeps driving the feared NPC away from wherever that player died, instead of resuming normal AI the way the puppet case does.
- Failure scenario: A player casts `GenjutsuNightmareItem` (fear) on an enemy, then dies (to that enemy or anything else) before the debuff's ~3+ second duration (`GenjutsuNightmareItem.FearDuration` plus any `GenjutsuControlDurationBonus`) runs out. For the remainder of that window, the feared NPC keeps fleeing a fixed point (the death location) instead of returning to normal behavior, which reads as broken/frozen AI right at a moment (a party member just died) when correct enemy behavior matters most.
- Suggested fix: Add the same `|| Main.player[ControllingPlayerIndex].dead` condition to `FleeMovement`'s early-return check, matching `PuppetMovement`.

## Improvements

### Robustness/Performance - `HitDebugLoggerPlayer` is a leftover TEMP debug hook still unconditionally attached to every player, scanning all NPCs and writing to disk on every single hit
- Location: Common/Players/HitDebugLoggerPlayer.cs:12-38
- Current: The class's own header comment calls it a "TEMP debug aid for tracking down 'something invisible is hitting me' boss reports" tied to the `TailedBeastBoss` investigation, and says "Remove once boss hitbox/position issues are confirmed fixed." That investigation appears to be exactly the one closed out by the 2026-09-21/22 `TailedBeastBoss` ground-cache fixes (`cd86f60`, `81016d7`), confirmed re-verified as recently as the 2026-09-23 report - but this file (added far earlier, in `e1aef71`) was never removed and has no gate behind a debug flag or `NarutoOverhaulConfig` option. Because it's a plain `ModPlayer` override with no scoping, `PostHurt` fires for every player on every single hit they take anywhere in the game (mob damage, fall damage, lava, PvP, not just boss fights), and each call does a full `Main.maxNPCs` (200) scan plus 1-3 `Mod.Logger.Info` calls that write to `tModLoader-Logs/client.log` on disk.
- Proposed: Delete the class now that the investigation it was built for is closed (per the file's own stated removal condition), or at minimum gate it behind a debug-only config flag/compile symbol so it isn't doing a 200-entity scan and disk I/O on every hit landed by every player in normal, non-debug play.
- Risk: trivial - this is debug-only instrumentation with zero gameplay effect either way; removing it (or gating it) changes nothing except log volume and a small per-hit CPU cost.

### Robustness - `smoke_test_server.sh` still always exits 0 even on a detected FAIL/exception, unfixed since first reported 2026-09-12
- Location: tools/smoke_test_server.sh:19-35
- Current: Confirmed still present by re-reading the file this run - the server launch line still ends in `|| true` (swallowing any nonzero exit), and neither the `FAIL: server did not report a clean start` branch nor the `WARNING: exception-like text found` branch is followed by `exit 1`, so the script always returns 0 regardless of what it printed.
- Proposed: Track whether either failure condition was hit and `exit 1` at the end (or immediately at each failure branch) so a CI/automation caller can actually gate on this script's exit code.
- Risk: trivial - purely additive, no change to detection logic.

### Robustness - `pixellab_generate.py`'s `edit_image` polling loop still has no timeout/max-retry cap, unfixed since first reported 2026-08-08/2026-09-10
- Location: tools/pixellab_generate.py:92-106
- Current: Confirmed still present by re-reading the function this run - `while True: time.sleep(5); ...` only exits on `"completed"`/`"failed"` status from the remote API; a job stuck in `"pending"`/`"processing"` forever polls indefinitely with no way to abort short of killing the process.
- Proposed: Track elapsed time/poll count and raise a `RuntimeError` past a max wait (e.g. 10-15 minutes) so a hung job fails loudly instead of hanging the art pipeline invisibly.
- Risk: trivial - purely additive bound-checking, no change to the success path.
