## Bugs

### Medium - TaijutsuKickItemBase.UseAnimation plays its dash + full-body VFX blast unconditionally, even when the paired Shoot() stamina spend fails
- Location: Content/Items/Weapons/Jutsu/TaijutsuKickItemBase.cs:41-51 (`UseAnimation` calling `PlayImpactFlash`/`PlayBlast`/`ApplyDash` with no gate, `Shoot` independently gating on `TrySpendStamina`); inherited unguarded by Content/Items/Weapons/Jutsu/IronLegItem.cs, Content/Items/Weapons/Jutsu/FrontLotusItem.cs, Content/Items/Weapons/Jutsu/LeafHurricaneItem.cs (none override `UseAnimation`)
- Description: `TaijutsuKickItemBase<TBlast>.UseAnimation` (the shared shape introduced in commit 974b099, "share Taijutsu VFX UseAnimation shape") spawns the impact-flash VFX, spawns the full player-anchored blast VFX, and pushes the player's `velocity.X` for the dash - all with no check on whether the swing will actually be able to pay its Stamina cost. The only stamina gate for these three items lives in `Shoot()`, which correctly does `return player.GetModPlayer<StaminaPlayer>().TrySpendStamina(StaminaCost);` - but `Shoot()` returning `false` only cancels the damage-dealing projectile (`IronLegKickProjectile`/`FrontLotusKickProjectile`/`LeafHurricaneKickProjectile`, since `Item.noMelee = true` and all damage comes from that shot). It does nothing to undo the VFX blast or the dash velocity that `UseAnimation` already applied.
  This is the exact bug class commit f571db9 ("fix: Rasengan/Gentle Fist free-cast on failed resource spend") fixed for `RasenganItem.Shoot()` and for `GentleFistItem` (whose `UseAnimation`/`ModifyHitNPC`/`OnHitNPC` now check a `_staminaSpent` flag before doing anything, per that same class's own comment: "GentleFist (no Item.shoot, so Shoot() below never fires for it) wraps its own stamina gate around base.UseAnimation instead of using the Shoot-based stamina spend"). That comment documents *why* GentleFist needed its own gate, but doesn't explain why IronLeg/FrontLotus/LeafHurricane's `Shoot()`-based gate is sufficient to prevent the same "get partial reward without paying" outcome - it isn't, because the VFX/dash live in a different hook (`UseAnimation`) than the one being gated (`Shoot`).
  In the common case `CanUseItem` already requires `Stamina >= StaminaCost` before the swing can start at all, so in practice `UseAnimation` and `Shoot` mostly agree. But `CanUseItem` and `Shoot()`'s `TrySpendStamina` are two independent reads of `StaminaPlayer.Stamina` taken at two different points in the item-use sequence, and nothing in this codebase enforces they happen in the same tick for every future change (e.g. a new stamina-draining debuff, an `autoReuse` edge case, or code added later that drains Stamina between those two points) - exactly the kind of latent gap the sibling fix was written to close everywhere else.
- Failure scenario: If `Stamina` is reduced between the `CanUseItem` check (start of swing) and the `Shoot()` call for the same swing - e.g. a future stamina-draining effect firing mid-swing, or any change that decouples those two checks by even one tick - the player gets the full dash-forward mobility and the full body-covering blast VFX for free, with `Shoot()` silently swallowing the failed spend and skipping only the projectile/damage. Today this manifests as an inconsistent contract more than a live exploit (no such mid-swing drain effect currently exists), but it is unguarded infrastructure sitting in the shared base class that three live items inherit, silently reintroducing the free-cast pattern the project already paid down once.
- Suggested fix: Give `TaijutsuKickItemBase.UseAnimation` the same explicit gate `GentleFistItem` already uses - spend stamina once in `UseAnimation` (e.g. via a `_staminaSpent` field or by having `UseAnimation` call `TrySpendStamina` itself and return early on failure) and have `Shoot()` reuse that already-decided result instead of re-rolling a second independent `TrySpendStamina` call. This also removes the current double-spend-attempt shape (one implicit check via `CanUseItem`, a second real spend via `Shoot`) in favor of a single source of truth per swing.
> Needs a decision: whether `Shoot()`'s existing `TrySpendStamina` call and `CanUseItem`'s check are guaranteed to observe the same `Stamina` value every tick (in which case this is a correctness/consistency cleanup, not a live exploit) - this needs confirming against tModLoader's actual per-tick call order for `UseAnimation` vs `Shoot`, which nobody has been able to verify in this environment (no local tModLoader/dotnet build - see `.bug-reports/NEEDS-INPUT.md`).

## Improvements

### robustness - HiraishinMarkerSystem.LoadWorldData assumes hiraishinMarkX and hiraishinMarkY are always the same length
- Location: Common/Systems/HiraishinMarkerSystem.cs:47-63 (`LoadWorldData`)
- Current: `LoadWorldData` reads `xs = tag.GetList<int>("hiraishinMarkX")` and `ys = tag.GetList<int>("hiraishinMarkY")`, then loops `for (int i = 0; i < xs.Count; i++)` and indexes both `xs[i]` and `ys[i]`. If a save file ever has mismatched list lengths (hand-edited, corrupted, or produced by a future save-format change that only touches one of the two lists), this throws an unhandled `IndexOutOfRangeException` on `ys[i]` and fails world load entirely, rather than degrading gracefully (e.g. dropping the trailing unmatched entries).
- Proposed: Clamp the loop to `Math.Min(xs.Count, ys.Count)`, or explicitly check `xs.Count != ys.Count` and log/skip the mismatched tail, so a partially-corrupt registry doesn't take down world loading for what is a purely cosmetic fast-travel convenience list (the world itself, and every other system, loads fine independent of this one).
- Risk: trivial - a bounds clamp with no change to the well-formed-data path.
