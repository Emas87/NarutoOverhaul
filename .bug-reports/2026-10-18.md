## Bugs
### Medium - KakuzuBoss's elemental phase transition can fake a mid-air "landing" during his Jump attack
- Location: `Content/NPCs/Bosses/KakuzuBoss.cs:220-245` (`UpdateElementPhase`) and `:353-380` (`IsGrounded`/`DoJump`)
- Description: `AI()` calls `UpdateElementPhase()` before the `switch` that
  dispatches to `DoJump()`. Whenever `NPC.life/NPC.lifeMax` crosses one of the
  five mask thresholds, `UpdateElementPhase` unconditionally runs
  `NPC.velocity = Vector2.Zero;` regardless of what `CurrentAttack` currently
  is. `DoJump`'s landing check is `IsGrounded() => NPC.velocity.Y == 0f`,
  used as `if (StateTimer > JumpTelegraphTicks && IsGrounded())`. If the
  threshold crossing happens on a tick where Kakuzu is mid-air with
  `jumpLaunched == true` (the normal case - combat damage is what drives the
  life ratio down, and a Jump attack can span many ticks while airborne),
  `UpdateElementPhase` zeroes `velocity.Y` to exactly 0 *this same tick*,
  and the very next statement block (the `switch`) calls `DoJump`, which
  reads that freshly-zeroed `velocity.Y` as "touched down" even though
  Kakuzu is still floating wherever he happened to be in his arc.
- Failure scenario: fight Kakuzu into a Jump attack, land enough extra
  damage mid-arc to push his HP ratio across a 20%-tier boundary (0.8/0.6/
  0.4/0.2) - trivial once he's below ~80% HP and a player is dealing
  continuous damage during the jump (fire/AoE DOT, a second player, a minion).
  `OnJumpLanding()` fires immediately at Kakuzu's current mid-air position:
  the landing VFX/sound/knockback-to-nearby-players triggers floating in
  mid-air instead of at the ground, `CurrentAttack` resets to `Recover` and
  `jumpLaunched` resets to `false` while Kakuzu is still airborne and still
  carrying his horizontal jump velocity (only Y was zeroed) - he then
  visibly keeps drifting/falling under gravity in the `Recover` state as if
  nothing happened, with the "landing" already consumed. Contrast with
  `OrochimaruBoss.UpdatePhase`/`DoSubstitution` (`OrochimaruBoss.cs:280-313`),
  which has the same per-threshold `NPC.velocity = Vector2.Zero` but also
  explicitly forces `CurrentAttack = AttackState.Recover` in the same call,
  so Orochimaru's `switch` never re-enters a movement state that trusts
  `velocity.Y == 0f` as "grounded" on a tick where that zero was synthetic.
  Kakuzu's `UpdateElementPhase` has no such override, so `CurrentAttack`
  stays `Jump` and the stale check misfires.
- Suggested fix: have `UpdateElementPhase` reset `CurrentAttack` to
  `AttackState.Recover` (and `jumpLaunched = false`, `StateTimer = 0f`) when
  it fires while `CurrentAttack == AttackState.Jump`, the same way
  Orochimaru's phase transition already forces a safe attack state after
  its own velocity reset - or, cheaper, have `IsGrounded()`/`DoJump` track a
  dedicated `grounded` flag set only from actual tile-collision contact
  instead of inferring it from `velocity.Y == 0f`, which any unrelated
  velocity write can spoof.
> Needs a decision: whether to fix by making the phase transition end the
> Jump state cleanly (matches the existing Orochimaru precedent, smallest
> diff) or to replace the `velocity.Y == 0f` grounded-proxy with a real
> tile-contact flag (more invasive, but removes the whole class of "anything
> that zeroes velocity fakes a landing" risk for future bosses too).
