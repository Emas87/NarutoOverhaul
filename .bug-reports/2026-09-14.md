# Audit report - NarutoOverhaul - 2026-09-14
3 bugs (0 high, 2 medium, 1 low), 1 improvement

## Bugs

### Medium - generate_armor_sheet.py can still silently clip the bottom of a Head frame (unfixed since 2026-09-10)
- Location: tools/generate_armor_sheet.py:162 (`HEAD_TOP_MARGIN`), :165-176 (`_center_on_canvas`), :213 (`build`, `anchor = "top" if args.equip_type == "head" else "bottom"`)
- Description: `_center_on_canvas` computes `scale = min(canvas_w / frame.width, canvas_h / frame.height, 1.0)` against the full 56px cell height (`CELL_H`, line 63), then for `anchor == "top"` (Head only) pastes the scaled frame at `y = HEAD_TOP_MARGIN` (10), not `y = 0`. The scale calculation never accounts for that 10px offset, so it only guarantees `frame.height <= 56`, not `frame.height <= 46`. Any Head content whose scaled height lands in 46-56px gets pasted starting at y=10 and running past `canvas_h=56`; `canvas.paste(frame, (x, y), frame)` on a Pillow `Image.new("RGBA", (canvas_w, canvas_h), ...)` clips silently — no exception, no printed warning. This is the exact same finding from `.bug-reports/2026-09-10.md`, still present verbatim in the code (line numbers unchanged, `git log` shows no commit touching this file since).
- Failure scenario: Running `python3 tools/generate_armor_sheet.py build --equip-type head ...` on a sliced-and-trimmed Head frame whose content is taller than 46px (plausible for any full headband/hair frame that fills most of the cell — the module's own comment notes the real reference `YewWoodHelmet_Head` frame was already 20px tall with margin, and AI-generated art isn't guaranteed to trim tighter) produces a Head equip texture with its bottom rows of art missing, with the tool printing nothing to indicate a problem — the same class of defect CLAUDE.md's "CRITICAL: real armor equip-layer template shapes" note already blames for one earlier "weird full-face head" bug, just via clipping this time instead of the wrong canvas shape.
- Suggested fix: When `anchor == "top"`, compute `scale` against `canvas_h - HEAD_TOP_MARGIN` (46) instead of `canvas_h` (56) — i.e. pass the usable height into the `min()` call, not the full cell height — so a full-height frame scales down enough to actually fit below the margin.

### Medium - PainBoss's Preta Path chakra drain still has no multiplayer-client guard (unfixed since 2026-09-08)
- Location: Content/NPCs/Bosses/PainBoss.cs:560-568 (`DoPreta`), called from the `AttackState` switch in `DoAttack`; contrast with the guarded siblings `DoAnimal` and `DoAsura` in the same file
- Description: `DoPreta` runs `if (NPC.Distance(target.Center) <= PretaDrainRadius && StateTimer % 10 == 0) { target.GetModPlayer<ChakraPlayer>().TrySpendChakra(8f); ChakraPlayer.SendCorrection(target); ChakraVFX.SpawnGenjutsuBurst(...); }` with no `Main.netMode != NetmodeID.MultiplayerClient` guard, unlike every other side-effecting `Do*` method in this file. `ChakraPlayer.cs:168-171`'s own comment states the assumption this depends on ("drains chakra server-side from AI(), which only ever touches the server's own authoritative copy") — that assumption is false: `NPC.AI()` runs on every connected peer's own local simulation of the boss, exactly why the sibling methods need their own guards. Verified still present, unchanged, across five prior audit reports (2026-09-08 through 2026-09-13); `.bug-reports/NEEDS-INPUT.md` records this repo's automated fixer finds and reviews this exact fix each run but discards it because the cloud environment has no dotnet/tModLoader test runner to verify a build against — so it stays a known, reviewed-but-unapplied fix rather than an oversight.
- Failure scenario: In a dedicated-server or listen-server game with a bystander client present (anyone other than Pain's current target and the host), that bystander's own local shadow simulation of PainBoss also executes `DoPreta` and calls `TrySpendChakra` on its own shadow copy of the drained player's `ChakraPlayer`. `ChakraPlayer.SendCorrection` only pushes the corrected value to the drained player's own connection (`packet.Send(player.whoAmI)`), never to bystanders, so the bystander's local Chakra shadow-copy for that player silently drifts and is never corrected.
- Suggested fix: Wrap the `TrySpendChakra`/`SendCorrection` block in `if (Main.netMode != NetmodeID.MultiplayerClient) { ... }`, matching `DoAnimal`/`DoAsura`; leave the VFX call outside the guard so it still plays for every client.
> Needs a decision: this fix has been reviewed and is ready three-plus times over, but keeps getting discarded unverified because there's no build/test runner in this environment. Options: (a) add a headless dotnet/tModLoader build check here so straightforward guard-fixes like this can actually be applied and verified going forward, (b) apply this specific one-line-guard fix manually since it's low-risk and mirrors an already-shipped pattern in the same file, or (c) accept it stays flagged-only and stop re-surfacing it in daily reports once it's acknowledged.

### Low - StarterItemPlayer's debug item giveaway still skips the multiplayer-client guard its sibling methods use (unfixed since 2026-09-08)
- Location: Common/Players/StarterItemPlayer.cs:59-96 (`OnEnterWorld` calling `GiveStarterItemsOnce`), contrast with the guarded `ForceStoryProgressUnlock`/`ForceTownNpcSpawn` in the same class
- Description: `OnEnterWorld` calls three methods; `ForceStoryProgressUnlock` and `ForceTownNpcSpawn` both open with `if (Main.netMode == NetmodeID.MultiplayerClient) { return; }`, but `GiveStarterItemsOnce` — which writes items straight into `Player.inventory` via `GiveItem` — has no such guard. Verified still present, unchanged, across five prior audit reports.
- Failure scenario: On a client joining a dedicated-server multiplayer game, `GiveStarterItemsOnce` runs and mutates that client's own local `Player.inventory` array directly with no accompanying network message — a raw slot assignment doesn't trigger tModLoader/vanilla's normal item-sync packets the way picking up or crafting an item does. The two guarded sibling methods in the same class treat this as the rule for the class; risks the granted items being invisible to the server/other players until some unrelated action forces a sync.
- Suggested fix: Add the same `if (Main.netMode == NetmodeID.MultiplayerClient) return;` guard used by `ForceTownNpcSpawn`/`ForceStoryProgressUnlock` at the top of `GiveStarterItemsOnce` (or `OnEnterWorld`, ahead of all three calls).

## Improvements

### robustness - extract_tmod.py still never closes the `.tmod` file handle it opens (unfixed since 2026-09-10)
- Location: tools/extract_tmod.py:53-71 (`parse_tmod`, `f = open(path, "rb")` at :55), used without a close anywhere in `main()` at :99-123
- Current: `parse_tmod` opens the file and hands the raw handle back to the caller for `extract_file` to `seek`/`read` from later; nothing in `main()` (or a `with`/`try/finally`) ever calls `f.close()` on either the `list` or `extract` path, so every invocation of this CLI leaks one open file descriptor for the process's lifetime. Confirmed unchanged since first flagged on 2026-09-10 — `git log` shows the only commit touching this file since (`f571db9`) added an `EOFError` message to `_read_7bit_string` and didn't touch `parse_tmod`/`main`.
- Proposed: Use `with open(path, "rb") as f:` in `parse_tmod` (returning the read bytes/entries instead of a live handle) or at minimum add `f.close()` at the end of both branches in `main()`.
- Risk: trivial. Low real-world impact since this is a short-lived one-shot CLI (the OS reclaims the descriptor at process exit either way), which is likely why it's stayed unfixed through two prior mentions — flagged again since it remains real and unaddressed.
