## Bugs
### High - `DelayedTileCollide` is a mutable reference-type field shared across every simultaneously-alive projectile of the same type, because `ModProjectile.Clone()` only shallow-copies it
- Location: `Common/Projectiles/DelayedTileCollide.cs:11-41` (the class itself), instantiated as a
  `private readonly` instance field in seven `ModProjectile` subclasses: `Content/Projectiles/
  KunaiProjectile.cs:20`, `ShurikenProjectile.cs:16`, `FumaShurikenProjectile.cs:15`,
  `ExplosiveKunaiProjectile.cs:26`, `MinatoKunaiProjectile.cs:23`, `WaterDragonProjectile.cs:23`,
  `SubstitutionLogProjectile.cs:23`
- Description: tModLoader creates one "template" instance of each `ModProjectile` subclass at mod
  load (e.g. `new KunaiProjectile()`), then gets a per-entity instance for every spawned projectile
  by calling `Clone()` on that template - whose default implementation (not overridden anywhere in
  this codebase; confirmed via `grep -rn "override.*Clone"` returning nothing) is `MemberwiseClone()`,
  a shallow copy. Value-type fields (the plain `int`/`float`/`bool` counters every other projectile in
  this codebase correctly uses for per-instance AI state, e.g. `WaterDragonProjectile.animFrame`) are
  copied by value and so stay independent per entity, which is why that pattern works everywhere else.
  But `delayedTileCollide` is a `class` (reference type) assigned once via a field initializer -
  `MemberwiseClone()` copies the *reference*, not the object, so every `KunaiProjectile` entity ever
  spawned in a given game session shares the exact same `DelayedTileCollide` object (and therefore its
  `spawnCenter`/`spawnCenterSet`/`ticksAlive` fields) as every other simultaneously-alive `KunaiProjectile`
  - and the same is true independently for each of the other six affected types.
- Failure scenario: `spawnCenterSet` is only ever set `true` once (`DelayedTileCollide.Update`,
  `if (!spawnCenterSet)`) and nothing ever resets it to `false`. So the *first* Kunai thrown in a
  session latches `spawnCenter` to wherever the player was standing at that moment, and every later
  Kunai thrown during the same session - from wherever the player has since moved to - reuses that
  stale, usually-irrelevant `spawnCenter` instead of its own spawn point, so
  `Vector2.Distance(projectile.Center, spawnCenter)` is essentially meaningless for it. Separately,
  `ticksAlive++` runs once per `Update()` call, and `Update()` is called once per AI tick *per active
  entity* - so with N Kunai in flight at once, the shared counter advances N times per game tick,
  reaching `fallbackTicks` (30, or just 6 for `SubstitutionLogProjectile`) many times faster than a
  single projectile's own real age would. Both effects push `tileCollide` back on far earlier than
  intended, re-triggering almost exactly the spawn-clipping bug this helper's own header comment says
  it exists to prevent: in ordinary play, simply throwing the starter Kunai (or Shuriken/Fuma Shuriken)
  more than once in quick succession - or two players throwing kunai near each other in multiplayer -
  makes the second and later copies liable to snag on the ground at/near the throw point instead of
  flying clear, intermittently depending on how far the player has moved and how many are in flight.
  `SubstitutionLogProjectile`'s dodge-log visual is the least affected in practice (its 12f/6-tick
  values are small and it rarely has multiple copies alive at once), but the weapon projectiles are
  the mod's most commonly spammed items, so this is live almost every time they're used more than once.
- Suggested fix: give `DelayedTileCollide` per-entity state instead of a shared object - either make it
  a `struct` (so `MemberwiseClone()`'s field-by-field copy produces independent state the normal way,
  matching every other per-instance counter in this codebase) or keep it a class but re-create it
  (`delayedTileCollide = new DelayedTileCollide(...)`) from inside each affected projectile's own
  `Clone()` override (or lazily on first `AI()` tick) instead of relying on the shared field-initializer
  instance. A `struct` is the smaller, more consistent change given how simple this helper's state is.

## Improvements
### Duplication - Taijutsu/Genjutsu/Ninjutsu Helmet and Legs armor pieces are near-identical copy-paste across 3 classes, with no shared base
- Location: `Content/Items/Armor/{Taijutsu,Genjutsu,Ninjutsu}HelmetItem.cs` and
  `{Taijutsu,Genjutsu,Ninjutsu}LegsItem.cs` (6 files; the matching `*BodyItem.cs` trio was already
  reviewed for correctness on 2026-10-06 but the duplication itself wasn't flagged there)
- Current: Each Helmet file is byte-for-byte identical in structure - same `Item.width/height`,
  `defense`, `value`, `rare`, the same `ArmorIDs.Head.Sets.DrawFullHair` static-defaults call, the same
  `UpdateEquip`/`ModifyTooltips` shape - differing only in which `*DamageClass` is passed to
  `GetDamage` and the class/namespace-comment name. The three Legs files are identical in the same way.
  This is the same shape of duplication already flagged (and, per `4acebf6`, already fixed) for the 7
  `BossSummonItem` subclasses, and already flagged-but-not-yet-fixed for the 5 village-headband items
  (2026-10-02/05).
- Proposed: extract a small generic/abstract base (e.g. `ClassHelmetItemBase<TDamageClass>` /
  `ClassLegsItemBase<TDamageClass>`) parameterized by damage class, stats, and set-name string, the
  same mechanical extraction already applied to the summon items - cuts 6 files down to a few lines
  each with no behavior change.
- Risk: trivial - purely mechanical, same low-risk pattern already proven out by the `BossSummonItem`
  extraction.
