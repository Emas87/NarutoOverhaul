and `FindEscapeSpot`/`FindClearTeleportCenter` in both files bound their tile

fully-solid arena - no issue there, only the interaction with `DoJump`.

## Bugs

### Medium - KakuzuBoss: the stuck-escape teleport mid-Jump fakes an immediate landing while still airborne, at the teleported-to location
- Location: Content/NPCs/Bosses/KakuzuBoss.cs:294-324 (`UpdateStuckState`), 364-389 (`DoJump`), 165-205 (`AI`, call order)
- Description: `AI()` calls `UpdateStuckState()` unconditionally every tick,
  before the `switch (CurrentAttack)` that dispatches to `DoJump` (lines
  182-202). `UpdateStuckState` tracks `stuckTimer` based on `embedded`
  (hitbox not clear of solid tiles, `IsAreaClear`) and `attemptingMovement`;
  critically, its final condition is `if (embedded || stuckTimer >=
  StuckToleranceTicks)` (line 318) - `embedded` alone fires it immediately,
  with no 180-tick wait. When it fires, it does `NPC.Center =
  FindEscapeSpot(); NPC.velocity = Vector2.Zero;` (lines 320-321) without
  looking at `CurrentAttack` at all. If this happens while the boss is
  mid-leap (`CurrentAttack == AttackState.Jump`, `jumpLaunched == true`,
  genuinely airborne with nonzero `velocity.Y`), the teleport+zero runs
  first, then the same tick's `switch` still calls `DoJump`, whose landing
  check `if (StateTimer > JumpTelegraphTicks && IsGrounded())` (`IsGrounded()`
  is just `NPC.velocity.Y == 0f`, line 362) is now true purely because of the
  zeroing just performed - not because the boss ever touched the ground.
  `OnJumpLanding()` (landing VFX + player knockback within
  `JumpImpactRadius`, lines 394+) fires at the freshly-teleported "escape"
  position instead of wherever the boss actually was in its arc.
- Failure scenario: Kakuzu's jump arc (horizontal + vertical impulse, several
  tiles of travel) passing its hitbox through or under any overhang/platform
  edge in the arena makes `embedded` true for even one tick while
  `CurrentAttack == Jump`; the very next `DoJump` call in that same tick
  instantly "lands" - the boss snaps to an unrelated nearby position, plays
  the landing flash/sound, and knocks back anyone standing near that new spot
  while still visually mid-fall, instead of actually completing the leap.
  Reproducible any time the fight has terrain tight enough for the jump's arc
  to clip it, which boss arenas with platforms commonly do.
- Suggested fix: in `UpdateStuckState`'s escape branch, mirror the guard
  `UpdateElementPhase` already uses: `if (CurrentAttack == AttackState.Jump)
  { CurrentAttack = AttackState.Recover; StateTimer = 0f; jumpLaunched =
  false; }` before (or alongside) the teleport, so the zeroed velocity can't
  reach `DoJump`'s grounded check later in the same tick, and the aborted
  jump transitions cleanly instead of firing a landing at the wrong spot.

### Medium - OrochimaruBoss: the same stuck-escape teleport mid-Jump fakes an immediate landing while still airborne
- Location: Content/NPCs/Bosses/OrochimaruBoss.cs:346-376 (`UpdateStuckState`), 492-517 (`DoJump`), 215-253 (`AI`, call order)
- Description: Identical mechanism and call order to the KakuzuBoss bug
  above - `AI()` calls `UpdateStuckState()` (line 239) before the `switch
  (CurrentAttack)` (line 253) that reaches `DoJump`. The escape branch here
  is `NPC.Center = FindClearTeleportCenter(NPC.Center, EscapeSearchRadius);
  NPC.velocity = Vector2.Zero;` (lines 372-373), again gated only by
  `embedded || stuckTimer >= StuckToleranceTicks` with no check of
  `CurrentAttack`. `DoJump`'s landing check (`IsGrounded()` ==
  `NPC.velocity.Y == 0f`, line 408) is satisfied by this zeroing in the same
  tick whenever the boss is mid-leap when its hitbox clips terrain.
- Failure scenario: same as KakuzuBoss - fighting Orochimaru near any
  platform/overhang his jump arc can clip triggers an instant, misplaced
  landing (VFX + knockback at the teleported-to spot) instead of a completed
  leap, any time `embedded` goes true for a tick while `CurrentAttack ==
  Jump`.
- Suggested fix: same shape as KakuzuBoss above - guard the escape branch
  with `if (CurrentAttack == AttackState.Jump) { CurrentAttack =
  AttackState.Recover; StateTimer = 0f; jumpLaunched = false; }` before the
  teleport/velocity-zero.

## Improvements

### Duplication/robustness - `UpdateStuckState` is duplicated near-verbatim between KakuzuBoss and OrochimaruBoss, including the gap that caused today's bugs
- Location: Content/NPCs/Bosses/KakuzuBoss.cs:294-324, Content/NPCs/Bosses/OrochimaruBoss.cs:346-376
- Current: both files define the same `embedded`/`attemptingMovement`/
  `stuckTimer`/`stuckWindowStartPosition` state machine with the same
  constants (`StuckToleranceTicks = 180`, `StuckMovementThreshold = 60f`,
  `MovingVelocityThreshold = 1.5f`, `EscapeSearchRadius = 150f`), differing
  only in the teleport-target helper name (`FindEscapeSpot` vs
  `FindClearTeleportCenter`). Neither copy knows about `CurrentAttack`, so
  the same oversight (today's bugs) shipped in both at once.
- Proposed: fold this into the same shared-helper discussion already open
  for the Jump-attack shape (see the bugs above) - a single
  `UpdateStuckState`/`AbortJumpIfActive` pair shared by any boss that has
  both mechanics would make this exact class of gap impossible to introduce
  in only one of the two copies.
- Risk: moderate - same caveat prior reports gave for the Jump-shape
  extraction: no in-repo test runner for boss AI, so this would need
  per-boss manual verification in-game rather than a mechanical merge.
