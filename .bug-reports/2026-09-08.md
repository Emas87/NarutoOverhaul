# Audit report - NarutoOverhaul - 2026-09-08
3 bugs (0 high, 1 medium, 2 low), 2 improvements

## Bugs

### Medium - PainBoss's Preta Path chakra drain is missing its multiplayer-client guard
- Location: Content/NPCs/Bosses/PainBoss.cs:560-569 (`DoPreta`), called from the AttackState switch at line 330-332
- Description: `DoPreta` calls `target.GetModPlayer<ChakraPlayer>().TrySpendChakra(8f)` directly on every tick the drain condition is met, with no `Main.netMode != NetmodeID.MultiplayerClient` guard. Every other side-effecting `Do*` method in this same file that spawns a projectile or NPC guards itself this way (`DoAnimal` at line 540, `DoAsura` at line 399, and the same pattern in HakuBoss.cs:249, KakuzuBoss.cs:322, MadaraBoss.cs:413, OrochimaruBoss.cs:453, KaguyaBoss.cs:441/489) — `DoAnimal`'s own comment even documents a bug that was once caused by this class's `StateTimer` timing, showing the guard convention is deliberate here. `ChakraPlayer.cs:168-171` documents the assumption this code depends on: "PainBoss's Preta Path drains chakra server-side from AI(), which only ever touches the server's own authoritative copy — without this, the client never learns their chakra was spent." That assumption is false as written: NPC.AI() (and therefore `DoPreta`) runs on every connected peer, not just the server, exactly the reason the sibling methods in this file need their own guards.
- Failure scenario: In a dedicated-server or listen-server multiplayer game with a bystander client present (someone other than Pain's current target and the host), that bystander's own local simulation of PainBoss also runs `DoPreta` and calls `TrySpendChakra` on its own shadow copy of the target player's `ChakraPlayer`. Chakra is a fully custom mod resource (unlike vanilla NPC life or Player velocity, it has no automatic vanilla net-sync) and `ChakraPlayer.SendCorrection` only pushes the corrected value to the actual target's own connection (`packet.Send(player.whoAmI)`), never to bystanders. The bystander's local Chakra shadow-copy for the drained player is now wrong and is never corrected, so anything that reads another player's Chakra client-side (a party UI, a hero-inspect-style panel, etc., now or in the future) can show a permanently incorrect value for that player on every client except the drained player and the server.
- Suggested fix: Wrap the `TrySpendChakra` call in `if (Main.netMode != NetmodeID.MultiplayerClient) { ... }`, matching `DoAnimal`/`DoAsura` immediately above it in the same file.

### Low - StarterItemPlayer's debug item giveaway skips the multiplayer-client guard its siblings use
- Location: Common/Players/StarterItemPlayer.cs:59-96 (`OnEnterWorld`/`GiveStarterItemsOnce`)
- Description: `OnEnterWorld` calls three methods: `ForceStoryProgressUnlock` and `ForceTownNpcSpawn` both open with `if (Main.netMode == NetmodeID.MultiplayerClient) { return; }`, but `GiveStarterItemsOnce` (which writes items straight into `Player.inventory`) has no such guard.
- Failure scenario: On a client joining a dedicated-server multiplayer game, `GiveStarterItemsOnce` runs and mutates that client's own local `Player.inventory` array directly, with no accompanying network message — unlike picking up or crafting an item, a raw slot assignment doesn't trigger tModLoader/vanilla's normal item-sync packets. The two guarded sibling methods in the same class treat "don't do inventory/world-state changing work as a plain MultiplayerClient" as the correct rule; this method doing the opposite is very likely an oversight rather than a deliberate exception, and risks the given items being invisible to the server/other players until some unrelated action (e.g. dropping the item) forces a sync.
- Suggested fix: Add the same `if (Main.netMode == NetmodeID.MultiplayerClient) return;` guard used by `ForceTownNpcSpawn`/`ForceStoryProgressUnlock`, or explicitly comment why this one is intentionally different if it is.

### Low - convert_gemini_sprite.sh's spill-cleanup pass silently no-ops for the script's own default background color
- Location: tools/convert_gemini_sprite.sh:99-107 (step 4, spill cleanup)
- Description: Step 4 auto-detects which channel `bg_color` is "dominant" in via two strict-inequality checks (`bg_g > bg_r && bg_g > bg_b` for green, `bg_r > bg_g && bg_b > bg_g` for magenta) and falls back to `spill_fx="a"` (a no-op — keep alpha as-is) otherwise. The script's own default `bg_color` is `#545454` (a neutral gray, r=g=b=84), which by construction can never satisfy either strict-inequality check, so `spill_fx` is always `"a"` for the documented default background. The file's own header comment (lines 4-20) explains at length why this pass exists ("faint background-tinted 'spill' on anti-aliased edges... a standard green-screen keying problem") and frames it as always running — there is no comment noting the gray-background case is a known, permanent no-op.
- Failure scenario: Any sprite processed through `convert_gemini_sprite.sh` using the default `#545454` background (i.e. every call site that doesn't pass a `bg_color` override) never gets the hue-based spill cleanup described in the file's own docs; only the fuzzy color-key + auto-trim from steps 1-3 runs. Any residual gray-tinted spill on anti-aliased edges is left in the final asset, silently, with no error or log line indicating cleanup was skipped.
- Suggested fix: Either give the gray/neutral case its own spill heuristic (e.g. compare per-pixel color distance to `bg_rgb` directly, the same fallback already used by `_is_background()` in tools/generate_armor_sheet.py / tools/slice_fx_sheet.py for a non-green/non-magenta custom color), or make the current behavior visible by printing a warning when `spill_fx` falls back to `"a"` so it's not mistaken for "nothing needed cleaning."

## Improvements

### robustness - land_icon.sh doesn't guard against no matching file in ~/Downloads
- Location: tools/land_icon.sh:24-26
- Current: `latest=$(find ~/Downloads -maxdepth 1 -type f \( -iname "*.jpeg" -o -iname "*.jpg" -o -iname "*.png" \) -printf '%T@ %p\n' | sort -rn | head -1 | cut -d' ' -f2-)` — if no matching file exists, this pipeline still exits 0 with `latest` set to an empty string (nothing in the pipeline fails), so the script proceeds to call `convert_gemini_sprite.sh "" "$dest" ...`, which then fails deep inside ImageMagick's `identify` on an empty path with a generic error rather than a clear message from this script.
- Proposed: After the `find`/`cut` pipeline, check `if [ -z "$latest" ]; then echo "No recent .jpeg/.jpg/.png found in ~/Downloads" >&2; exit 1; fi` before invoking `convert_gemini_sprite.sh`.
- Risk: trivial

### maintainability - VFX burst dispatch in ChakraVFX.cs is one hand-written wrapper method per effect type
- Location: Common/VFX/ChakraVFX.cs:56-71 (`SpawnChakraBurst` ... `SpawnImpactBurst`, 15 near-identical one-liners)
- Current: Each burst effect gets its own public static method that only differs by its generic type argument, all delegating to the same private `SpawnBurstEffect<T>`. Call sites already reference the effect type directly when using `SpawnPlayerAnchoredBurst<T>` a few lines below (line 78), showing the codebase is comfortable calling the generic method directly with an explicit type argument.
- Proposed: Either drop the 15 wrapper methods and have call sites use `ChakraVFX.SpawnBurstEffect<FireBurstProjectile>(position, scale, rotation)` directly (making `SpawnBurstEffect<T>` public), or keep the wrappers if the named-method call sites are considered meaningfully more readable — this is a low-stakes readability/duplication tradeoff, not a defect, flagged only because a 16th effect family means a 16th copy-pasted one-liner forever.
- Risk: trivial (pure refactor, mechanical, would touch many call sites' import lists if wrappers are removed)
