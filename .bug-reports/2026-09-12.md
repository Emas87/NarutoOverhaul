2 bugs (0 high, 1 medium, 1 low), 2 improvements

## Bugs

### Medium - smoke_test_server.sh always exits 0, even when it detects FAIL or an exception, silently defeating the pre-commit gate every doc tells you to trust
- Location: tools/smoke_test_server.sh:26-40
- Description: The script's own header and three separate project docs (`ROADMAP.md:6`, `ARMOR_HEAD_LEGS_REWORK_2026-08-05.md:96`, `ICON_REGEN_TODO.md:23,176`, plus `.claude/skills/armor-body-sprite/SKILL.md:91` and `.claude/skills/vfx-blast-sprite/SKILL.md:151`) describe this as a pass/fail gate ("both must pass") to run before committing. But the script never calls `exit 1` on failure. The server launch itself is intentionally forced non-fatal (`... || true`, correct - `timeout` returning nonzero on a normal shutdown shouldn't kill the script under `set -e`). After that, the two checks are:
  ```
  if grep -q "Server started" "$LOG"; then
  	echo "PASS: server started cleanly."
  else
  	echo "FAIL: server did not report a clean start - check the log above."
  fi

  if grep -qiE "exception|unhandled" "$LOG"; then
  	echo "WARNING: exception-like text found in the log - review above."
  fi
  ```
  Neither branch (`FAIL:` nor the exception `WARNING:`) calls `exit 1` or otherwise sets a nonzero exit status, and a failed `if` condition does not trigger `set -e` (that's standard bash - a condition being tested is expected to be able to fail). The script's final exit code is therefore always 0 regardless of what the log actually shows.
- Failure scenario: A change breaks content loading (bad texture path, duplicate content ID, exception during `Autoload`/`SetStaticDefaults` - exactly the class of bug this script exists to catch per its own header comment). Running `tools/smoke_test_server.sh` prints `FAIL: server did not report a clean start` (or a `WARNING:` about an exception in the log) but the command still reports success (`echo $?` → `0`). Anyone or anything treating "the script passed" as "exit code 0" (a CI step, a wrapper script, a habit of glancing at the last line instead of reading the whole log) ships the breakage.
- Suggested fix: Track pass/fail in a variable and `exit 1` at the end if either check failed, e.g. set `ok=1` on the FAIL/WARNING branches and `exit 1` after the trailing checks if `ok` is unset - or simply `exit 1` directly in the `else`/exception-found branches (the `WARNING` case is arguably still worth surfacing as a failure too, since "exception-like text present" is exactly the failure mode this script is meant to catch, not just an FYI).
  > Needs a decision: should a log containing exception-like text (the `WARNING:` case) also fail the script, or is that deliberately just informational because it can include false positives (e.g. an NPC named "Exception" or benign caught-and-logged framework noise)? If the latter, the fix should still make the `FAIL:` (no clean start) branch exit nonzero, and could leave `WARNING:` as an intentional non-fatal grep for a human to skim.

### Low - land_icon.sh silently proceeds with an empty path when ~/Downloads has no matching image, instead of failing with a clear message
- Location: tools/land_icon.sh:24-26
- Description: `latest=$(find ~/Downloads -maxdepth 1 -type f \( -iname "*.jpeg" -o -iname "*.jpg" -o -iname "*.png" \) -printf '%T@ %p\n' | sort -rn | head -1 | cut -d' ' -f2-)`. If `~/Downloads` has no matching files (e.g. it doesn't exist yet, or everything already got moved into the repo), `find` succeeds with empty output, so the pipeline's exit code is 0 under `set -euo pipefail` and `latest` becomes an empty string - `set -e` never fires because no command in the pipeline actually failed. The script then prints `using  -> Content/Items/...` (empty filename, visible but easy to miss) and calls `convert_gemini_sprite.sh "" "$dest" ...`, which fails several steps in inside `identify -format "%w" ""` with an ImageMagick error like `identify: unable to open image '': No such file or directory`.
- Failure scenario: Running `land_icon.sh` right after clearing out `~/Downloads` (or before the Gemini download has actually finished/landed) gets a confusing ImageMagick traceback from a downstream script instead of land_icon.sh's own clear "no image found in ~/Downloads" message - wastes a debugging cycle chasing the wrong script.
- Suggested fix: After computing `latest`, check `if [ -z "$latest" ]; then echo "No .jpeg/.jpg/.png found in ~/Downloads" >&2; exit 1; fi` before the `echo "using ..."` line.

## Improvements

### robustness - extract_tmod.py opens a .tmod file handle that is never closed
- Location: tools/extract_tmod.py:55 (`parse_tmod`, `f = open(path, "rb")`), used without a close in `main()` at :103-123
- Current: `parse_tmod()` opens the `.tmod` file with a bare `open(path, "rb")` (not a `with` block) and returns the live handle for `list`/`extract` to keep reading from later (offsets are computed lazily, so the handle has to stay open across the call). `main()` then uses that handle in the `list`/`extract` branches but never calls `f.close()` on any code path, including error paths that `sys.exit()` before reaching the end of `main()`.
- Proposed: Either wrap `main()`'s handle usage in a `try/finally: f.close()`, or add an explicit `f.close()` at the end of each branch in `main()`. (A `with` block isn't a direct drop-in since the handle needs to outlive `parse_tmod()`'s return, but `try/finally` around the two branches in `main()` covers it cleanly.)
- Risk: trivial - the process exits right after either branch today so the OS reclaims the handle regardless, but this is a short-lived-script exemption, not a fix; a future caller that imports `parse_tmod`/`extract_file` as a library function (e.g. a batch-extract loop) would accumulate open handles.

### robustness - pixellab_generate.py's job-polling loop has no timeout or retry cap
- Location: tools/pixellab_generate.py:92-106 (`edit_image`'s `while True` poll loop)
- Current: `while True: time.sleep(5); status = _get(f"/background-jobs/{job_id}", key); ...` only exits via `return` (on `"completed"`) or `raise RuntimeError` (on `"failed"`) - any other terminal-looking state (the API wedges on `"queued"`/`"processing"` forever, or a transient network blip raises inside `_get` since it only catches `urllib.error.HTTPError`, not `URLError`/timeout) leaves the script polling or crashing with no way to distinguish "still legitimately working" from "hung."
- Proposed: Add a max-attempts or wall-clock timeout (e.g. `for _ in range(max_polls): ...` or track elapsed time against a `--timeout` arg) and raise a clear `RuntimeError("Job <id> did not complete within Ns")` when exceeded, so an automated batch run (this is explicitly a batch-asset-generation tool per its docstring) fails fast and visibly instead of hanging indefinitely.
- Risk: trivial (additive change to a standalone dev tool, no behavior change on the success path)
